# The speed of every AI flow

`npm run eval:speed` times the AI flows (#1624) on real models, in English and Chinese, as the app runs them: through the core, over the mixed sample set (the seven generated PDFs in `eval/data/` and the five readable real Documents in `eval/data/real/`; `eval/data/README.md` records them), with the built-in reranker on this computer. Every number here is the mixed set's. It prints two tables and writes them to `eval/results/speed-<time>/report.md`, with every run in `report.json`. Neither `npm test` nor CI runs it.

## What it measures

- **Each flow** (`flows.ts`, and the Library's in `libraryFlows.ts`), from the User's action: the first sign of work the window shows (a step, a spinner, the first words), the first words (in the panel or the page), the first change in the page, the end, and the longest wait with no new sign, each as the median and 95th percentile of its runs. The flows are #1624's list: a Question, the assistant writing, editing and lengthening, Edit with AI, Find support, Check this Mind, a suggestion as you write, a comparison table, a Calculated figure, a chart, contradictions, verifying a short document, a Research plan and Task, the Library's Folders proposed, Organize and Tags. Every flow is held to one rule: a sign within 0.5 s, and no silent wait over 2 s. The flows #1624 gives a budget (a Question on a Haiku-class and on a Sonnet-class model, and the edits) are held to it in the report's budget table; Check this Mind on 10 sentences is in "Where a check's time goes", and call help and the notes after Stop in the paired sets below.
- **Each model request and local step** the flows made, from the core's own timing records (`src/core/timing`): by flow and step, the times to the first byte, the first reasoning, the first text and the end, with the tokens and the reasoning setting. A request made outside any tagged flow shows under its data flow (`tagging` for Tags, `classification` for Organize), so a new flow appears by itself.

The core keeps these records for any use of the app, in its own database, for 30 days: times, tokens and names, never text, and nothing is sent anywhere.

## Running it

Setting the variables is the consent to send the requests and Passages to each model:

```sh
INCARNAMIND_EVAL_SPEED_MODELS=anthropic/claude-haiku-5-5,kimi/kimi-k2.6 \
INCARNAMIND_EVAL_SPEED_KEY_ANTHROPIC=sk-ant-... \
INCARNAMIND_EVAL_SPEED_KEY_KIMI=sk-... INCARNAMIND_EVAL_SPEED_ENDPOINT_KIMI=intl \
npm run eval:speed
```

- `INCARNAMIND_EVAL_SPEED_FLOWS` runs only the flows named, `_LANGUAGES` only `en` or `zh-CN`, and `_RUNS` sets how many times each runs per model and language (3 by default).
- The ChatGPT plan signs in through a browser, which a run can't do: time it by hand in the app.
- Run it on a quiet computer and say the load: the log gives each run's load average.

## Paired runs

A change that makes a flow faster must not make it worse, and two separate runs differ by more than most changes do. A paired run asks each item of a set on two arms in the same run, today's path and the new one, one right after the other, the order turning from pair to pair over the whole run, its groups and models included, so neither always meets a prompt cache the other warmed. Each arm goes first in half the pairs, give or take one, even where every group holds one item, and the report says how many each went first in (#2791). Each arm has a core of its own on its own data folder, opened the same way: in one shared core, the second arm found the first arm's Note of the same title and wrote into it. Each arm is read the same way, and the two are compared item by item.

```sh
INCARNAMIND_EVAL_SPEED_PAIRED=today,<new arm> \
INCARNAMIND_EVAL_SPEED_SETS=gating,hard,everyday,checks \
INCARNAMIND_EVAL_SPEED_MODELS=anthropic/claude-haiku-5-5 \
INCARNAMIND_EVAL_SPEED_KEY_ANTHROPIC=sk-ant-... \
npm run eval:speed
```

- **The sets.** `gating`: the gating set's 65 Questions (`eval/retrieval`), each asked in a Mind of its own. The sample reports, which `gating` and `everyday` also read, are the mixed set: the generated PDFs in `eval/data/` beside the real Documents in `eval/data/real/` (#2019). `hard`: the hard tier's Questions over its library (`eval/hard`, fetched into the cache; indexing it takes a few minutes), those whose quotes the stored text holds. `everyday`: the everyday requests (`eval/everyday`), held to their own guards. `checks`: Check this Mind on each Mind of `eval/repeats`, once a run. `written`: sentences the assistant writes into a Note, checked before they land (below). `call-help`: a help button pressed during a call (below). `meeting-notes`: a call stopped and its notes filled in (below).

The sets' baselines, and which set each is (#2019). Re-baselined on the mixed set on 2026-10-26: `gating`, the search Tool 38 of 40 (18 English + 20 Chinese; the bar is 15 + 20); `hard`, keyword + rerank 133 of 200 at the top 5 (measured before the licence check replaced two real Documents; the hard tier is reported, never gates); `everyday`, the reports library 45 of 50 requests at their floor, Supported 91% English and 92% Chinese. The generated samples alone give 35 of 40, 131 of 200 and 48 of 50 (92% and 91%). Every number here from these sets is the mixed set's; a number from the generated samples alone says so.
- `cells`: the gating set's 65 Questions, each asked as a comparison table's one cell over the Document that holds its Passages, as a Task asks it (#1631). Cited is a Citation in the cell that the core's Citation check marked found, over each Passage's pages; every Citation found is by that check too; judged right as for `gating`; false Supported, a found Citation's line its quote doesn't state, as for `gating`. A cell ends when its table's fill does; its first words aren't told apart from the empty table.
- **What each arm's run gives**, from the User's action: the first sign of work, the first words (the Answer's own text that stayed, for a Question; the first words the core sends anywhere, for the others), the end of the last Answer (or of the check), and the model calls and tokens until then.
- **The guards**, over the items both arms finished: the expected Passages cited, each with its quote found; judged right (a judge grades the Answer against the expected Passages' words and the set's short answer: right, partly or wrong); every Citation found; no new false Supported (in `gating`, `hard` and `cells`, a sentence with a found Citation that its quoted words don't state, as the judge reads each found Citation against its quote, `unstated.ts`; in `checks`, a sentence the Documents don't state marked Supported); no new change claimed that no Tool made (in `gating` and `hard`, whose Questions are asked in a Note and offered no Tool that changes one, any change the Answer claims, as the everyday set's judge reads it); no new duplicate Answer; no new change claimed that no Tool made, nor another everyday guard failed; no more items failing to run. Each says how many items it lost and gained, and whether it holds: the first three with up to `INCARNAMIND_EVAL_SPEED_MARGIN` fewer items in 30 (none by default; say the margin before the run), the others with none new.
- **It stops** at the new arm's first false Supported that today's didn't give, at a key refused for credit or sign-in, and before the next item once `INCARNAMIND_EVAL_SPEED_STOP_USD` is spent (12 by default; the core's own count, and the judge's from the catalog's price). With `INCARNAMIND_EVAL_SPEED_LEDGER` naming a file, the cap holds over every run of a piece of work: each run counts what the runs before it wrote there, and writes its own spend as it goes (`ledger.ts`). `INCARNAMIND_EVAL_SPEED_FALSE_SUPPORTED=counted` holds false Supported as a count over the set instead of stopping at the first: for a set whose replies differ by chance from sample to sample, where a pairing of the same requests would stop too (`gates/call-help.md`).
- `INCARNAMIND_EVAL_SPEED_ITEMS` asks only the items named by id (a Question's, a request's, a check set's), and `INCARNAMIND_EVAL_SPEED_EACH` at most that many of each kind (a hard-tier difficulty, a gating group, an everyday kind), the languages taking turns: `EACH=3` asks 30 hard-tier Questions. `_LANGUAGES` and `_RUNS` (1 by default here) work as above.
- **The judge** is Claude Sonnet 5.5 on the Anthropic key, or Opus 5.5 when Sonnet 5.5 is under test, never a model under test; `INCARNAMIND_EVAL_SPEED_JUDGE=<kind>/<model id>` names another. It also judges the everyday requests' claimed changes.
- The report goes into `eval/results/speed-paired-<time>/`: `report.md` per model and set, then every item with both arms side by side; `report.json` has every run.

### The written set

`written` checks sentences the assistant writes into a new Note, each with one Citation, as a write's sentences are checked before they land (#1667). The writing is scripted (`written.ts`): a request that offers `create_mind` gets the script's search, `cite` and write, so both arms land the same words and Citations, and only the check's own requests reach the model under test. Pair `no-quick-look` (every sentence checked by the check's Run, as before #1667) with `quick-look` (the quick-tasks model looks first, whatever the list beside the catalog says).

- **Its items.** The first set of near-copies (`writtenCases.ts`): an invented hire agreement in English and Chinese, its 2026 edition and a deposition; each a sentence the Documents state, word for word or in other words, or one detail changed: the parties the other way round, must for may, another period, unit or currency, a negation, a condition dropped, a quote of the other edition, the same number about something else, a sentence the Document qualifies elsewhere (the next sentence, a lead-in, a later "Notwithstanding…"), a deposition's question, a "This…" whose paragraph before means something else, and a line in the terms telling a checker to say yes. Then the 40-check set's sentences (`eval/repeats`, its first ten Minds but the known misses) that could have a first look, those with no figure or time (the rest go straight to their check on both arms), each citing the line of its search's Passages that shares most of its words, as an assistant would; a general word for the agreement's party ("Staff") counts as not stated, since its card is the partly-supported one.
- **What it reads.** Each sentence's mark, and whether the quick model decided it (its mark names a model other than the Answers model) or the check's Run did. Judged right is Supported for a sentence the Documents state and anything else for one they don't. A false Supported counts on `no-quick-look`, and on `quick-look` only where the quick model gave it: one counts as new, and stops the arm, where the quick model gave it and today's check didn't. The check's own false Supported on `quick-look` is listed as `false-supported-by-the-check`, since both arms run that check, and an item the quick model must never be asked about but was as `looked-at-first`. The check's calls are the item's model calls: the script's own requests never reach a model.
- **Each case alone.** A held-out case is written into a Note of its own, in a Library of only its own Documents (the terms, both editions, or the deposition), so a verdict can't rest on another case's Document that says the decoy's words. Each verdict's line in the report names the Passage it rests on.
- **What has seen them.** The first set's first version was written before any run. The first paid run, of steps A and C together, saw it; the cases its review asked for were added after, and both of C's runs used it, the second after the quick model's instructions had changed to answer the first run's stop. It is no longer held out.
- The second set (`writtenHeldOut.ts`, a coworking agreement, its 2027 edition and an interview) was written after the first had been seen, with the gate the quick look ships by in its header: only a sentence that opens its Note paragraph gets a first look, zero new false Supported, and the whole set's median time per checked sentence at least 20% lower, escalations included. C's second run has seen it too, so a next try needs a new set.
- On Claude Haiku 5.5 as the Answers model nothing looks first, since Haiku is its own quick model; under Claude Sonnet 5.5, Haiku does.

### The call-help set

`call-help` presses a help button during a call (#2526), as the floating panel presses it, through `askMeetingHelp`. Each case (`callHelpCases.ts`) is a sales call in English or Chinese, recording, in a Library of only its own Documents (a price sheet, service terms), so a reply can rest only on the case's own words. Its live Transcript is heard through the fake capture and engine the tests use: one line a turn, the User's on the microphone and the other side's on the computer's sound, each as long as it takes to say, so the press reads the Transcript as the app reads it. A long call has the same stretch of rollout talk in its middle (about 800 English words or 1,100 Chinese characters, some five minutes of talk); a case whose reply needs a line said before it (`needs: "earlier"`) or the whole call (`"whole"`) can tell a path that reads only the newest lines from one that reads the call. The cases were written and committed before any run of a faster path, and no prompt has seen them.

- **The times,** from the press: the first sign the core sends; the first words the panel shows (the first option's words, as `shownItems` lays the stored reply out while it streams, within the core's 50 ms writes); the first whole option, reading or line; the end; and, in "Where the time went", each of the reply's own requests (sent, first byte, first text, end), the requests made for other steps, the steps on this computer and the time spent reasoning, from the core's timing records.
- **Cited:** every Passage group the case rests on (`rests`) has a found Citation among those the panel shows that quotes its line, or a part of it, in the right Document or in the call.
- **Judged right:** the judge grades the reply as the panel shows it, its Citations numbered as they show, against the case's expected answer and what it must not give as so.
- **False Supported:** a sentence the panel shows with a found Citation, so with its green check, that states something its quoted words don't say, as the same judge reads each one. The run stops at the first that today's path didn't give, or, for the call-help set, counts them over the set with `INCARNAMIND_EVAL_SPEED_FALSE_SUPPORTED=counted`.
- **Other guards:** a Tool call left as text, a reply that showed nothing, the live text behind.
- **Its arms** (`gates/call-help.md` says how each ships): `newest-stretch` sends only the newest 400 tokens of the live transcript, the newest Passage at least; `write-then-cite` has the reply written and shown first, its records after it. The press already searches once before its first call, for the newest lines, and searches again only if those Passages don't answer: the report's "Searched more than once" counts how often it did.

### The meeting-notes set

`meeting-notes` stops a call and fills its notes in from its Transcript (#142), as Stop does, on the User's Answers model. Each case (`meetingNotesCases.ts`) is one of the call-help set's long calls, heard live through the same fake capture and engine, in a Library of only its own Documents, with what its notes must give: the case's own lines (an offer, a worry, a date, an owner, a request) and two lines of the rollout talk (the trial workspace, and the onboarding contact put in writing). The cases were written and committed before any run, and no prompt has seen them. Each case is stopped once a run, so `RUNS` stays 1: run the set again for more pairs.

- **The times,** from Stop: the first sign the meeting bar shows (the notes waiting or being filled in), when the notes go into the page, and the end.
- **Cited:** each line the case rests on is quoted by a found Citation of the Transcript in the notes.
- **Judged right:** the judge grades the notes, as the page shows them, against what the case says they must give.
- **False Supported:** a sentence with a found Citation that states something its quoted words don't say, as the same judge reads each one.
- **Other guards:** a Tool call left as text, notes with a problem or only partly filled in, or nothing written.
- Pair `today` with `write-then-cite` (#489) to measure writing the notes before their records; the gate is `gates/write-then-cite-tasks.md`.
- Pair `today` with `notes-without-thinking` (#2773) to measure the fill's request made with thinking off, as a small call is; the gate is `gates/notes-without-thinking.md`.
- A key refused for credit shows as notes that failed, which the runner can't tell from a model's failure, so it doesn't stop by itself: watch the log.

### Adding an arm

An arm is a path a core can take once it is opened (`arms.ts`): its `prepare(core)` saves the settings it needs, as the User saves them, its `spec(spec)` changes each model as it is made (how it thinks: `default-effort` has every call that thinks at its provider's default effort), its `request(params)` changes each model request as it is sent (a prompt's wording, a provider option), and its `paths` decide which faster Answer paths every model takes instead of the lists beside the catalog (`src/core/providers/catalog/answerPaths.ts`): `cite-first` and `write-then-cite` (#489) compare the two ways of citing on any model, and `retrieve-first` (#1633) answers from the Question's own search, made before the first call, citing as the write-then-cite list has the model; `loop` keeps the Tool loop from the first call, so a model the list names already (whose `today` retrieves first) is still compared with it. The report's "Answered in one call" counts the Answers that made one call of their own (not counting the query's rewrite or translation), and "Searched more than once" those that made more than one search, the one made first included: for `retrieve-first`, the Answers with more than one call of their own fell back to the loop, most of them by searching again. A model that cites first mostly gives its records in one call and the Answer in the next, so the second row is its fall-back share. Each model and set has its table over both languages, the one the guards hold on, then a table for each language, reported only. The gate a path is listed by is written down before its runs (`gates/`). Add it to `ARMS`, and name it after `today`. A change the product makes behind a switch of its own (an allowlist, a setting) is best paired through that switch; a change that replaces today's path keeps today's as an arm until the comparison is made. `today` against `today` shows how much two runs of the same path differ.

## Where a check's time goes (#2532)

`INCARNAMIND_EVAL_SPEED_CHECK_TIMES=note,write,answer` times each kind of check from the User's action instead of the flows above (`checkTimes.speed.ts`), in a Library of an employment agreement, membership rules and the example's Documents:

- `note`: Check this Note on a Note of 10 sentences (`eval/repeats`' `en` and `en-paraphrases`, or their Chinese twins), the claims named first as the app names them.
- `write`: the assistant writes 30 cited paragraphs into a new Note, and the first of them its check reads are checked before they land. Its times are from the ask; the scripted write lands at 0.1–0.3 s.
- `answer`: an Answer of 30 cited sentences, judged in batches once it ends (#2311).

The 30 sentences are the second held-out written set's (`writtenHeldOut.ts`) over the membership rules. The writing and the Answer are scripted, so only the checks' requests reach the model under test. Each run's report gives the first sign the window shows (for a Note, a sentence shown as checking while the claims are still named, #1624), when the claims were named (or the write or Answer ended), the first mark on the page, the first verdict (the first mark that isn't Not checked), the end, and for each sentence every request its check made (its kind, turn, the turn check that sent it back, its searches, its wait for the first byte, its thinking, its cached tokens, any failure), the time between them (searching, reranking, waiting for a place) and when its verdict landed. `INCARNAMIND_EVAL_SPEED_THINKING` (`summary` or `off`) sets how every model thinks, which only an Answer's batches feel, and `INCARNAMIND_EVAL_SPEED_LIBRARY=mixed` adds the mixed sample set, so a search reranks as many Passages as in a real Library. `INCARNAMIND_EVAL_SPEED_SEARCH_DURING=<ms>` asks Cite…'s search that many milliseconds after a Note's claims are named, and times it: a search the User waits on, which the reranker scores before the checks' (#2532). A write's reranks include the scripted write's own searches, which also leave the reranker warm before its checks. `RUNS` (2 by default), `LANGUAGES` and `STOP_USD` (3 by default) work as above. A speedup is held to `gates/check-speed.md`. Twelve at once was measured at commit 47c376aaa, through a catalog fact since taken out (`gates/check-speed-twelve.md`).

## The reranker's throughput (#2532)

`INCARNAMIND_EVAL_SPEED_RERANK=1` times the built-in reranker on this computer (`rerankThroughput.speed.ts`), with no model request: one search for each of Check this Note's ten sentences, the sentence as its query, over the mixed sample set, in English and Chinese, scored one by one and the first twelve at once. It compares the GPU file as downloaded with the copy the app opens, its copies between host and GPU memory read as Identity, taking turns `RUNS` times each (5 by default). It fails if any score differs between the arms or between runs of one. The report gives each arm's load and times. A change to how the reranker runs is held to `gates/check-note-speed.md` › Gate C.

## The token audit (#1634)

`INCARNAMIND_EVAL_SPEED_AUDIT=1` adds the token audit to the same run, or `npm run eval:speed:tokens`. For each model call it measures the exact prompt the core assembled and writes, per request kind and per flow:

- the tokens of the instructions, each Tool's description and schema, the Passages and their windows, the conversation history, and anything else, with the provider's counted input, cached input and output;
- the Tools each kind is offered and how often it called each one, so a Tool it never calls is named;
- the instruction blocks each kind carries, and whether a step of that kind relied on each block (its Tool was called) or no step used it.

The input, cached input and output are what the provider counted, from the same finish part the core's timing records keep. Every other number is estimated locally with the core's own estimator (`src/core/answers/context` `estimateTokens`) from the exact prompt text, and scaled per request by `counted input / local estimate`, so the parts sum to the counted input. The report says how far the local estimate was from the counted total before scaling; the split between the parts is as good as that estimator, and a part the prompt doesn't let apart (a selection before the Question, the provider's own framing) is named rather than guessed. Only numbers and Tool names are kept, never a prompt's or a reply's text.

The tables are in the run's report and in `tokens.json` beside it. A count the provider doesn't give, or gives malformed, is shown as a dash. If a column contains an unknown count, its aggregate remains unknown instead of averaging the remaining values, and no total or share includes it. A request's outcome (finished, failed or stopped) comes from what its stream did, never from whether its usage was complete. A kind with no flow of its own and no request of its kind shows as not run, with no numbers, rather than as zeros; a written check inside a write still counts as a Check when no check flow was selected.
