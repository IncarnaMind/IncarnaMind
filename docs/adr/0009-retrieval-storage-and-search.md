# Retrieval uses node:sqlite, in-memory vectors, multilingual-e5-small and segmented FTS5

## Context

ADR-0008 and spec #20 left storage and search open. The retrieval prototype (#21) settled them on 20 questions (10 English, 10 Chinese) over seven sample PDFs and five Chinese Wikipedia articles, plus 5 cross-lingual questions. **Hit rule:** a question is a hit when one of the top 5 Passages covers the expected page and contains the expected quote. One question is 10 points of a language, so a difference of one question is not evidence. Timings are from an Apple M2 Max. The `prototype/*` branches are no longer on `origin` (#2004); the measurements stand as recorded.

## Decision

- **Driver: `node:sqlite`.** It runs FTS5 in Electron's main and utility processes with no extra package, and matched better-sqlite3 on lookups and queries; bulk inserts were 1.4 times slower, small next to embedding.
- **Vectors: brute-force cosine in memory, not sqlite-vec.** Embeddings are float32 blobs on the Passage rows. Same top 50 as sqlite-vec, faster at every size (40 against 62 ms at 100,000 Passages; 4.6 against 34 ms for a Search scope of a twelfth of them), for 154 MB of memory and 0.2 to 0.3 s to load at 100,000 Passages.
- **Keyword search: FTS5 with the default `unicode61` tokenizer over text pre-segmented with `Intl.Segmenter`,** which is in Node's ICU data, so there is no dependency and the index stays small.
  - **Traditional Chinese reads as simplified** (#67), in the index and in queries, with the Citation check's table, before the text is split into words; the stored text keeps its characters (`src/core/documents/keywords.ts`). With embeddings off nothing else bridges the two scripts.
  - **A Document's name has a keyword index of its own** (#2042), one row a Document. A Passage's row holds only its own words. Keyword search adds `DOCUMENT_NAME_WEIGHT` (1) times the Document's name score to each Passage's BM25 score, reading the name index once a search. A Document whose name matches still returns all its Passages, so naming a Document filters to it. Why: a name in every row counted once per Passage, so its IDF fell as the Document grew, and a long report's name pushed a needed Passage out of the search Tool's top 20. It costs about 17 ms more a keyword search at the median. Migration 111 creates the index; the host rewrites old rows in the background (`upgradeKeywordIndex`), one Document a transaction, from stored text. The start never waits, and a Document not yet rewritten stays searchable. The name index is derived and device-local, never synced.
- **Embeddings are off by default** (2026-10-10, decided with the User). Search is keyword search (FTS5, BM25), reranked, plus a second search in the Documents' language for a cross-lingual Question. No embedding model is downloaded, loaded or run unless the User turns embeddings on in Settings → Document search, where "Off" sits beside the built-in model and the providers. A Document is ready once its keyword index is.
  - **Why:** keyword, vector and hybrid search were level on the gating Questions (32, 31 and 32 of 40); the reranker made the difference (36). Embeddings cost a 135 MB download, a process of up to 0.9 GB, most of the processing time, and with a cloud provider the text of every Document.
  - **Turned on,** Documents are embedded in the background and search is hybrid: each list's top 50 fused by reciprocal rank fusion (k = 60), then reranked. A Passage with no vector yet counts its keyword rank for both lists; a Search scope with no vectors yet is searched as with embeddings off.
  - **Upgrades:** an install on the built-in model, the old default, goes off; one with a chosen provider stays on. Stored vectors are kept and reused if the User turns the same model back on; only Passages without one are embedded.
  - **Reopened** if hybrid + rerank beats keyword + rerank by more than one Question in a language on the paraphrase Questions or the hard tier, or if Users miss Passages worded unlike their Questions.
- **Reranking** (#31). A built-in cross-encoder, mmarco-mMiniLMv2-L12-H384 (Apache-2.0, int8 ONNX, 136 MB, in its own utility process; ADR-0005), reranks the candidates, not the fused list, because fusion pushed out hits only one search found. It took English from 13 to 16 of 20. Until the model is downloaded, or when the User turns reranking off, search keeps its own order.
  - **Candidates** (2026-10-12, #543): with embeddings off, keyword search's top 20 (`keywordRerankCandidates`); with them on, keyword search's top 10 and vector search's top 10. Keyword search alone ranks Passages worded unlike the Question lower, so it gets more. Its top 60, used from 2026-10-10 to 2026-10-12, took twice as long (1.6 against 0.8 s a search) for nearly the same Passages handed.
  - **Where it reranks** (2026-10-12, #542): one-search Answers, Suggest as I write (which reads its score for a strong match, #282), checks and comparison tables. **A model's own searches in the Tool loop (ADR-0007) skip it:** that model rewrites its queries and searches again, so the reranker added nothing measurable and was most of an Answer's time (about 1.6 s a search, 2 to 3 searches an Answer). A model that answers from one search loses Questions without it (91 against 107 of 180 hard-tier Questions).
  - **Checks skip it too** (2026-11-18, #3326, decided with the User): a check's model searches in a Tool loop as an Answer's does, so its searches keep search's own order, or the decision model's reading where one is in use (#3118). Measured on Claude Haiku 5.5 beside `main` with the built-in reranker: of 342 sentence-checks of the repeated-checks sets 315 got their expected verdict without it and 310 with it, false Supported 0 and 0; Check this Note of 10 sentences over the mixed sample set finished in 8.8 s against 12.1 s in English and 9.0 s against 10.8 s in Chinese at the median of four runs, judged right 36 and 36 of 40 against 36 and 37. A comparison table's cells are checked the same way, so they skip it as well. It still reranks one-search Answers, Suggest as I write and a search a person reads the results of (Cite…, a figure's sources).
- **The reranker runs on the GPU where it can** (#270), 3.9 times faster at the median and within one gating Question of the CPU. Where onnxruntime-node's WebGPU provider finds an adapter (bundled, as experimental, for macOS arm64, Windows x64 and arm64, Linux x64), it runs the fp16 file `onnx/model_O4.onnx` of the same pinned revision (235 MB, size and SHA-256 recorded) in batches of 8; WebGPU has no kernels for int8's quantised operators.
  - The fp16 file is downloaded only after onnxruntime finds an adapter. The int8 file always downloads and is the fallback, run one pair at a time, since batching changes its scores. Each load checks the GPU against the fp32 model's scores for a fixed query and three texts (within 0.1 logits); with no adapter, a failed session or a failed check it reranks on the CPU and logs why, since onnxruntime has open wrong-output bugs on some GPUs (microsoft/onnxruntime#32938, #32134, #24442).
  - It opens a copy of the fp16 file with its twelve CUDA `MemcpyFromHost` nodes read as `Identity` (#2532): same scores, 4 to 11% faster. The copy is a 235 MB file, since a session opened from rewritten bytes took 60 to 110 MB more memory. A copy that fails gives way to the downloaded file, and is kept where both fail so it isn't rewritten at every start.
  - Settings → Search says "On this computer · GPU" or "· CPU". The evaluation runs where the app would, or on the CPU with `INCARNAMIND_EVAL_RERANK_CPU=1`.
- **What a search hands the model** (2026-10-12, #543): a one-search Answer (such as a small local model's) gets at most 12 Passages, up to 3 windows from each of 4 Documents, which found many more Questions answered in two places (126 against 107 of 180 hard-tier Questions). A model in the Tool loop keeps 8: it can search again, and with 12 Claude Haiku 5.5 stopped citing on a Question it cited with 8. A local model's window keeps the most relevant Passages first.
- **No query rewrites by default.** Two more phrasings by a chat model found the most (38 of 40) but cost a model call before every search and send the Question out before any Passage is found; in the Tool loop the model writes its own queries anyway.
- **Cross-lingual Questions:** search finds Passages best in their own language, so the search Tool names the Documents' languages and tells the model to search again in them (ADR-0007).
- **Built-in embedding model: multilingual-e5-small, int8 ONNX** (`Xenova/multilingual-e5-small`, MIT, 384 dimensions, 135 MB). It found 14 of 20 with vectors alone against 15 for bge-m3, at a quarter of the download and a sixth of the indexing time; it peaks at about 0.9 GB. Passages are embedded with their Document's name, **one at a time**: batches were no faster, doubled peak memory and made int8 embeddings depend on the rest of the batch.
- **Passages: about 500 tokens with 200 overlap,** each recording a sliding window of 3 (step 1), with approximate token counts (one per CJK character, one per four characters otherwise), built the prototype's way: whole lines fill a Passage, the next starts with a tail of whole lines, and each line counts in whole tokens (hybrid search found 17 of 20, against 15 at the old 400/200, with a third fewer Passages). #25's sentence-break builder lost English questions at these sizes (#31). The window of 3 was not tuned: the hit rule scores single Passages.
- **Text is normalised before it is embedded or indexed:** NFKC, plus folding the CJK radical look-alikes it misses (browser-made PDFs encode `大` as `⼤`, 8% of the fixtures' Chinese characters), and no whitespace next to CJK characters (pdf.js adds it). The Passages a chat model reads are stored text, with only the radical look-alikes folded, as every other reader folds them (#67).
- **Schema: plain SQL migrations with a small runner** that records each in `schema_migrations`, so migrations built in parallel land in any order. Search needs FTS5 virtual tables, which Drizzle's tool can't generate, and Drizzle's stable release has no `node:sqlite` driver. All pending migrations run in one transaction, on a worker thread with its own connection while the first window loads, closed before the core opens the file (#2104); no worker starts when the file already records the latest. The core still runs the runner when it opens the database, so a host without threads, or a failed worker, migrates there.

## The Citation check matches quotes more forgivingly than indexing reads text

`findQuote` (`src/shared/quoteMatch.ts`), which the viewer's highlight uses too, reads the quote and the page alike. None of this changes `normaliseText`, so no Document is processed again.

- **Case, markers, hyphens:** lower case, "[^N]" as "[N]", a soft or line-end hyphen in or out (and followed by a space), and more quote marks and dashes unified. The 2026-10-07 run had marked 3 of 12 English Citations "not found" for these.
- **An ellipsis marks words left out:** the quote is found when each part is on the cited pages, in order, and every part has at least 3 words and 15 letters or digits, since a shorter part would match almost anywhere. The viewer highlights each part. The answering prompt still asks for one unbroken stretch.
- **Simplified and traditional Chinese, character by character** (#67): both sides read traditional as simplified, by OpenCC's `TSCharacters.txt` (Apache-2.0, from `opencc-data` 1.4.2, a devDependency), generated by `scripts/hanVariants.ts` into `src/shared/hanVariants.ts`: 2,966 one-to-one pairs, so offsets hold. A phrase another region writes differently ("披露" for "揭露") stays "not found". Answers quote in the script they write (ADR-0007).
- **f-ligatures, only where a Document's text lost them** (#67): pdf.js reads some PDFs' "fi" as "f". A Document lost them when it has at least 200 "f"s before a letter and under 5% before "f", "i" or "l" (`lostLigatures`); only there is a quote's ligature read as one "f". Ungated, 3.8% of other words would match another ("of" an "off"), a changed word. The core decides once per Document version from all its text; the PDF viewer from the PDF's text, so its highlight agrees.
- **Table cells and slides** (#76, ADR-0011): a pipe between cells reads as a space, and a slide's quote is tried again with number formatting normalised.
- **Quoted words may run on to the next page** (#2504), in the check of an Answer's quoted words only (#483): from the one page a record cites to the Document's next page, never past it, never for a record citing two pages or for slides or sections, and every ellipsis part must start on the cited page. The card says "The quote continues on p. 12."
- **Nothing else is forgiven,** because "found" must keep meaning these words are on the page: a reworded quote, or one from another page, stays "not found" (`tests/eval/recordedCitations.test.ts`). Left out on purpose:
  - **A quotation mark matches only its own kind** (curly double with `"`, curly single with `'`), so a nested quote in the other kind is "not found": in code the kind carries meaning (`“users”` names a table, `‘users’` is a string), and every rule tried let some SQL with a changed meaning through.
  - **A bracketed gloss in another language** ("（英語：deep networks）") is part of the page's words: a word list can't tell a translation from a qualifier.
- **One rule for quoted words wherever a Citation is checked** (#2712): `quotedWordsVerdict` (`src/core/answers/quotedWords.ts`) judges for the Answer's check, a landing in a Note, Recheck, Edit with AI, Update the sentence…, Replace, "already cited" and the assistant's writing into a Note, so a verdict can't change by moving a Citation. The renderer never reads a page: it asks the core, and until the core answers only words inside the cited quote count. A Citation's own quote and Location never run on to the next page.
  - Sentences are the shared splitter's (`sentenceSpans`). For quoted words only, an opening quotation mark after a sentence's end starts a sentence (`Revenue rose. “the fee…”`, `增长了。“`) unless the splitter reads on past the stop; and a sentence doesn't end inside quotation marks but after their closing marks and brackets (`.”)`), unless a line break comes first.
  - A recheck knows only its own Citation, read only where the Note may read it, so it never grants a translation. Only the Answer, which sees every Citation of the sentence, does, and then it stores no words to check again.

## Considered options

- **better-sqlite3 13:** the fallback; faster bulk inserts, but a native dependency we don't need.
- **sqlite-vec 0.1.9:** slower than a loop at every size; pre-1.0, no Windows on Arm build, one more native library to sign. Revisit it, or quantise the vectors, well past 100,000 Passages.
- **Other embedding models:** bge-m3 was the best, and the best across languages, but too slow on a CPU; snowflake-arctic-embed-m-v2.0, gte-multilingual-base and paraphrase-multilingual-MiniLM-L12-v2 scored lower. Users who need better cross-lingual search can choose an API or Ollama model (ADR-0005).
- **Other rerankers:** bge-reranker-v2-m3 tied at four times the download and twelve times the time; gte-multilingual-reranker-base changed nothing.
- **Passages of 150 to 600 tokens:** smaller lost English questions; at 600, most English Passages pass the 512 tokens e5-small reads.
- **FTS5 `trigram`:** fewer hits, an index six times larger and queries twice as slow.
- **No segmentation:** a run of Chinese characters is one word, so Chinese never matches.
- **Drizzle 1.0 release candidate:** every search query needs raw SQL anyway, and it isn't final. Revisit when 1.0 ships if hand-written queries become a burden.

## Consequences

- The gate (`eval/README.md`) is what the search Tool hands an Answer with embeddings off: 15 of 20 English and 20 of 20 Chinese gating Questions, on the int8 CPU file.
- The process that runs search keeps a Search scope's vectors in memory, in step as Documents are added and deleted.
- Integers bound through `node:sqlite` must be `BigInt` where SQLite checks types (virtual tables, `STRICT` tables): it binds every JavaScript number as a float.
- Chinese questions over English Documents are weak with the built-in model: it favours Documents in the question's language.
- The evaluation set and the Chinese fixtures live in `eval/retrieval/` (Wikipedia fixtures under CC BY-SA 4.0, see `eval/retrieval/fixtures/ATTRIBUTION.md`).
