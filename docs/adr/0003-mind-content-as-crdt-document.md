# Each Mind is stored as one CRDT document (Yjs)

Each Mind's content is a single Yjs document that the editor edits directly. It is not stored as one database row per Block with a numeric order. We chose this because the hosted version must sync Minds across devices (ADR-0002). Yjs merges edits made offline on different devices without conflicts, so adding sync later means relaying updates, not migrating data. It also removes the job of translating editor changes into insert/reorder/delete calls, which the old frontend never got working. The cost is that finding Blocks in a Mind, such as the ones above a Question, means reading the document instead of running a query.

## Consequences

Version 1 has no sync, but it follows these rules so sync can be added without migrating data:

- A Document is known by where its file belongs, its Linked folder and its path inside it, never by a path on one device, and a hash of its content identifies each version (ADR-0020). This replaced identifying a Document by its content hash, which ADR-0010 had already narrowed.
- Every ID is a random UUID generated on the device, never an auto-increment number, so two devices can't produce the same ID.
- Deleting something marks it deleted rather than removing the row, so a later sync can tell other devices about the deletion.
- Secrets (API keys, OAuth tokens) are kept only on the device and never go in data that will be synced.
- Settings are split into per-device (window size, file paths) and per-User (default model, interface language). Only per-User settings will sync.

## Amendment: kinds, a content schema version, one reference shape, and Citations

Chats now, and sheets, decks and boards after the alpha, are stored the way Minds are, so the storage leaves room for them and stays safe once Minds sync between computers running different versions.

- **Kind.** Each Mind has a `kind` on its row, `mind` by default (`chat` for a chat). A Mind of a kind this version doesn't know is listed, but it opens as "Update IncarnaMind to open this", never in the editor, and the core refuses to write to it.
- **Content schema version.** A Mind's Yjs document records, in its settings map, the content schema version it was last written with (`CONTENT_SCHEMA_VERSION` is the newest this version understands: 2 since tables, #92, 3 since footnotes, #284, 4 since Proposals, #93, 5 since a Proposal records the text it changes, #94, 7 since charts, #436, 8 since Document chips and checklists, #115, 11 since AI text, #95, 14 since a chart value's scale, #579, 15 since what a Word import keeps as it is, #104, 16 since the rows a cut chart doesn't draw, #503, 17 since comparison tables, #98, 18 since checks of the User's own sentences, #96, and 19 since contradiction watch's action, #112). A Mind with none reads as version 1. The core records its version on every write and never lowers one. A Mind written by a newer version opens read-only with a notice to update: the editor's Yjs binding deletes node types and marks, and strips attributes, that its schema doesn't know, which would silently destroy another computer's content once sync exists. For such a Mind the core neither compacts nor accepts any update, so its Yjs state stays byte for byte as it was. Raise the version whenever a change would make an older version lose or misread content (a new node type, mark or attribute). A raise that only adds node types needs no rewrite of older Minds: their content is valid as it is, and they record the new version on their next write. A chart (version 7) is such a node: it keeps the Citation of each value it draws in its own attributes, and the start-up walk that keeps the versions Citations quote reads them there too. So is a comparison table (version 17), whose cells hold their Citations as nodes, as an Answer does. The same holds for a raise that only adds marks or attributes: version 4 adds the `proposalInsert` and `proposalDelete` marks and a `proposal` attribute on Blocks and inline nodes, which older content simply doesn't have, and version 5 adds a `target` to them, without which a Proposal is never out of date. Version 8 adds node types: the `documentChip` inline node the User writes with "@", which names a Document by its id (and keeps its name as it was, for when the Document is gone), and the `taskList` and `taskItem` nodes of a checklist, whose items keep `checked`. A field inside an attribute counts too when an older version would write the attribute again without it: version 14 adds `scale` to each value in a chart's `data`, which an older version keeps while it changes a chart's kind, columns or title, but drops when its Update writes the values again, and version 16 adds `cutRows` to that `data`, which an older Update drops the same way.
- **Proposals are content, kept with the Mind.** A change the AI made that waits for the User (a Proposal) is stored in the Mind's Yjs document itself, so it survives sync and reload and any device can resolve it: words it removes stay, under `proposalDelete`, and words it adds are there, under `proposalInsert`; a whole Block or an inline node it adds or removes carries the `proposal` attribute (the editor's Yjs binding keeps no marks on nodes). Each names its Proposal and the request that made it; a `proposalRequests` map beside the Blocks says which model made each request, and is kept once written. Accepting or rejecting is one Yjs change, defined once (`src/shared/proposals.ts`) for the core and the editor. What reads a Mind's text (Question context, exports) reads it as accepted: without what Proposals add, with what they would remove.
- **One reference shape.** A reference from one artifact to another is `{ artifactId, anchor }`. The anchor is a Block's stable ID for now (`{ kind: "block", blockId }`), never a position, so the reference survives edits and sync. It is used for a Block's origin and for the link back from a Note to the chat it came from.
- **Citations stay editor-independent.** A Citation's target is always a Document location (a Document and where in it), independent of the editor and of the artifact that holds the Citation. Citations are checked against Documents, never against Blocks or any artifact's structure, so a Citation means the same in a Mind, a chat or a later kind of artifact.

## Amendment: conversations are not Minds (2026-10-11, ADR-0017)

The assistant's conversations are kept by the core in SQLite, not as Minds (ADR-0017), so two things above change. The `chat` kind is retired: `mind` is the only kind this version opens, and `kind` stays for sheets, decks and boards. And a reference names its artifact's kind, `{ artifactKind, artifactId, anchor }`: a Mind's anchor is a Block, a conversation's is a message (`{ kind: "message", messageId }`). A reference stored without `artifactKind` is a Mind's. Citations stay as above: a Citation in a conversation is checked against its Document like any other.

## Amendment: where third-party text came from (2026-10-11, #78)

A Mind's Yjs document keeps, beside its Blocks, a `textOrigins` map: for each Block, top-level or nested, that holds third-party text (ADR-0013, amended), where it came from ("imported", "web-page" or "checked-document"), by Block id. It is a map rather than a Block attribute: an attribute would have to be declared on every node type a Block can be, nested ones too, and an older version's editor would strip it unless the content schema version rose, which would make every Mind written since open read-only there. An older version keeps the map as it is, so the content schema version stays 4. A Block deleted since leaves its entry unused. A copy pasted elsewhere gets a new id and counts as the User's, as text pasted from another app does.

## Amendment: when each line of a Meeting's notes was written (2026-10-12, #139)

A Mind's Yjs document keeps a `blockTimes` map beside its Blocks: for each line the User writes while the Meeting records, the Meeting's time in ms, by Block id. It is a map for the same reason as `textOrigins`: an attribute would make an older version's editor strip it, or need the content schema version to rise, so the version stays as it is. A line takes its time when it first has text, a Mark when it is made, and nothing is taken while the Meeting is paused or stopped. A Block deleted since leaves its entry unused; a copy pasted elsewhere has no time.

## Amendment: AI text is a mark on its words (2026-10-12, #95)

The words the AI wrote that the User hasn't made their own carry a `generated` mark, kept in the Mind's Yjs document as a formatting attribute of their text, so it survives sync and reload and any device draws it the same. It is a mark, not a map beside the Blocks like `textOrigins`: it belongs to words, not Blocks, and has to split and follow them as the User types inside AI text, which only text formatting does. What the User types never takes it, and "Mark as mine" takes it off. Older Answers have no marks; an Answer written since carries `generatedMarks: true`, and one without is AI text as a whole, as it always was. An older version's editor would strip the mark and the attribute, so the content schema version is 11; nothing older is rewritten. Readers and exports treat the mark as no mark.

## Amendment: a Mind imported from a Word file (2026-10-12, #104)

A Mind can be imported from a .docx (ADR-0011, amended), and export writes the User's edits back into the original package (#105), so the Mind keeps what that needs.

- **Content schema version 15** adds three node types: `wordAtom`, inline, and `wordBlock`, a Block, for what the editor can't represent and keeps as it is (a field, a text box, a bookmark, a header…), each naming where its XML is in the package; and `image`, an inline picture. Older content is version 15 content as it is. A version before 15 opens a Mind with any of them read-only.
- **Beside the Blocks,** two maps, as `textOrigins` is, so an older version keeps them as they are: `word` (the file: its name, the package's SHA-256, size and main part; whose document it is; what the import made editable and kept as is; how far the import has got) and `wordSources` (for each node mapped from a paragraph or a table, by node id: its `w14:paraId` or its place in the part, and its fingerprint as imported, which tells export whether it was edited).
- **The package** isn't in the Yjs document: it is kept in the data folder by its SHA-256 (ADR-0011), with a row per Mind (migration 75), and would sync as a file of its own.

## Amendment: a sentence's check is a mark on its words (2026-10-13, #96)

Find support and Check against Documents put a `claimCheck` mark on the sentence they checked, holding the result and what it was made from: the sentence's text as checked, the Document versions the check read, and the scope. It is a mark for the same reason AI text is: it belongs to words, splits and follows them as the User edits, and goes when they are deleted. It isn't inclusive, so words typed after the sentence aren't under it. Whether a check still holds is worked out from what it records, so nothing is rewritten when a Document changes. Its evidence's version is retained under the Mind (`retained_versions`, kind `check-result`) rather than found by the start-up walk. An older version's editor would strip the mark, so the content schema version is 18; nothing older is rewritten. Readers and exports treat the mark as no mark. Contradiction watch (#112) marks a cited sentence another Document contradicts with the same mark and a third `action`, "contradiction-watch", whose Check again leaves out the Documents the sentence cites. Version 18 reads an unknown action as Find support, whose Check again would check the sentence against those very Documents, so the version is 19; nothing older is rewritten.

## Amendment: someone else's tracked changes are Proposals (2026-10-13, #108)

Another person's insertions and deletions in an imported Word file (ADR-0011, amended) are stored as Proposals, with the same marks and `proposal` attribute as the AI's, so they are accepted and rejected the same way, on any device. Each is named by where its change is in the file (`word:` and its place), and its request records who made it and when, as the file says (`{ source: "word-change", author, date }`), the same records each time the file is read. They are never read as if they weren't there when out of date: the Word export writes them back as theirs. An older version's editor keeps the marks, but would take the changes for the AI's and count what accepting one keeps as AI text, so the content schema version is 20; nothing older is rewritten.

## Amendment: a Word file's look is kept with the Mind (2026-10-14, #746)

A Mind imported from Word shows the file's own look: its tables' lines and shading, alignment, indents, tab stops, fonts, sizes and colours. The import reads each style once, resolved as Word resolves it (the document's defaults, the table's style, the paragraph's style chain, the list level, the run's character style, then direct formatting), and keeps it in the Mind, so drawing it reads no XML and typing, Undo, Proposals and sync carry it as they carry the text.

- **A `wordLook` map beside the Blocks** holds the styles (`WordLook`), each once, under a key made from the style itself (a short hash), so a key names the same style in every Mind: it grows with the number of styles the file uses, never with its Blocks. A pasted key the Mind doesn't have came from another file, and the paste drops it. It is a map for the same reason `word` is, and it holds a few whole values, since the styles don't change once read and two devices reading the same package write the same ones.
- **The Blocks name their style:** a `wordLook` attribute on paragraphs, headings, tables and cells, which Enter copies to the new paragraph (`keepOnSplit`), as Word gives a new paragraph the one before's properties; and an inclusive `wordRun` mark on text, which what is typed at its end takes, as Word's typing takes the run's formatting. Only text unlike most of its paragraph carries the mark; the paragraph names that main run look (`run`), so a long file's text is mostly unmarked and opens quickly. A look that is underlined, struck, highlighted, shaded or raised is never a paragraph's main run, since drawn on the paragraph it would cover all its text. Joining two paragraphs gives the moved text the first one's main run look, until typing in the look (#746) marks moved text with its own. A paragraph also names the look Enter gives the next one when its style says (`next`, Word's `w:next`).
- **Content schema version 21.** An older version's editor would strip the attribute and the mark, so it opens these Minds read-only. Older content is version 21 content as it is.
- **The look isn't content.** A node's fingerprint (`wordFingerprint`) leaves the attribute and the mark out, and joins text only the mark split, so giving a Block its look doesn't make export treat it as edited, and export writes the file's own bytes for what the User didn't change. Readers and exports treat the mark as no mark.
- **Minds imported before** get the look once, at a start, in the background, from their kept package: only the Blocks still as imported (their fingerprint, as it is now or as earlier versions recorded it, is the one recorded at import), found by the place their source names; a Block the User changed keeps the plain look. Their fingerprints are recorded again as this version computes them. Every change is planned and checked before any is made, in one change; the core's change is no Undo step in the editor. A Mind whose look an earlier version read (its map's `version` is lower) has the look cleared, attributes, marks and map, and given again at the next start, on the Blocks still as imported. `word_packages.look_version` (migration 90) records it, so it never runs twice and a start needn't read each Mind to find out.

## Amendment: what a check couldn't read (2026-10-15, #740)

When Find support, Check against Documents, Check this Mind or Verify starts, the files in its scope that couldn't be read (a format not read yet, a scan with no text, a locked, damaged or too large file) are kept in a `checkUnread` map beside the Blocks, by the request that made the checks, as they were then. The line beside the checks and the AI use statement say what wasn't read when the checks ran, not what isn't read now. Each file is kept by its name, reason and Document, never by its path, which belongs to one computer. A request that read everything has no entry, and an entry no check's mark names any more goes when the next request is recorded, so the map holds no more than the checks the Mind shows. It is a map rather than an attribute of the `claimCheck` mark: one list per request, not one per sentence, and an older version keeps it as it is, so the content schema version stays as it is.

## Amendment: the assistant reads its own changes still waiting, and revises them in place (2026-10-15, #893)

The assistant read a Mind as accepted, as Question context does: without what its own Proposals add. Asked to "make the summary longer" right after writing it, it found the page empty and wrote a second summary under the first, or said it couldn't change text that waits. In four of five test runs the page ended with two overlapping versions.

- **The Mind as the User sees it.** The Mind in focus and `read_mind` read every change still waiting as a change (`reviewReading`): the AI's as waiting ("[waiting change, adds: …]", "[waiting change, removes: …]"), someone's from a Word file with who made it, as before (#734). A change of the AI's that is out of date is read as if it weren't there, as accepting every change leaves it. Everything else that reads a Mind's text, Question context in a Mind and the exports included, still reads it as accepted.
- **The assistant revises its own waiting Blocks.** Blocks an Answer in the assistant added whole (a request of source `answer-added`), still waiting, all AI text, are its own. `edit_mind` over them rewrites that text as it reads once accepted, in a copy of the Mind, by Edit with AI's instruction or with new text the model gives (`content`), and puts the new Blocks in their place, still waiting, as a new request (`src/core/proposals/ownWaiting.ts`). The User's text is never touched, since none is in them. Over any other change still waiting, or own Blocks beside the User's text, nothing changes and the Answer says so, with Review.
- **What a revision replaced is kept.** A `revisions` map beside the Blocks (`MIND_REVISIONS_FIELD`) keeps, by the revising request, the Blocks it replaced and the id of the Block before them. Rejecting all of that request, or writing its Answer again, puts them back exactly as they were; accepting any of it lets them go. An older version would reject the revision and lose them, so the content schema version is 22.

## Amendment: paragraph formatting, and a Word file's direct formatting is the User's (2026-10-18, #912)

The User sets a paragraph's alignment, indents, spacing and line spacing, and text's colour, font, size and raise, in any Mind. A Mind imported from Word keeps the formatting its paragraphs and runs set themselves in the same place, so the Aa menu shows and changes it.

- **Content schema version 24** adds the `paragraphFormat` attribute on paragraphs and headings (`ParagraphFormat`), which Enter copies to the new paragraph, and the `textColor`, `textFont`, `textSize`, `superscript` and `subscript` marks. An older version's editor would strip them, so it opens these Minds read-only. Older content is version 24 content as it is.
- **The look keeps what styles give.** From `WORD_LOOK_VERSION` 6 the look keeps what the file's styles and lists give; what a paragraph or run sets itself, where a format or mark can say it, is the paragraph's format and the text's marks. A paragraph whose styles give nothing but which sets something itself has the empty look, so it still draws as Word draws it, not in the Mind's style. Export compares the format and marks with the file's and writes a property only where they differ.
- **An edited Block no longer stays plain.** When the look is read again, a Block the User changed keeps their text and their own format, and is given the file's direct formatting it lacks: the format's values the User didn't set, and the marks of the words still as the file has them, so export doesn't take those for the User's change. If the Mind had a look before, the Block gets its look back too; one changed before the Mind had any look gets the format and marks but no look.
- **Until the look is read again,** a Mind whose look an older version read lacks the file's direct formatting, so export keeps the file's where the Mind has none, never removing it.

## Amendment: a check the User keeps as their own view (2026-10-18, #1111)

Keep as my view, on the card of a cited sentence found unsupported, sets `kept: true` on that sentence's `claimCheck` mark. While its words stay as they were checked, the sentence shows no mark, isn't counted in the Mind's health, and no check runs on it again (Check this Mind in every mode, contradiction watch); editing the words ends it. It stays on the mark, beside the result, so ⌘Z takes it back with the words' other changes in one step. An older version's editor strips mark attributes it doesn't know, so it would drop `kept`, and the `unsupported` reason a check gives (#1072), and count and check the sentence again: the content schema version is 25. Nothing older is rewritten.

## Amendment: a Mind's chosen Search scope, and the scope a check looked in (2026-10-23, #1623)

The Search scope the User sets for a Mind in its composer is where its Questions search and its checks look. "Ask about this Document" and text added from an Answer asked of one Document set it too.

- **The scope is Mind content.** It is a `scope` key in the Mind's settings map (`MIND_SETTINGS_FIELD`), beside its model, so it goes wherever the Mind goes, syncs with it and survives a restart. A Mind with no key has no scope of its own and is checked as before: in its Folder while that holds a Document, else in every Document.
- **One whole value.** The key holds the scope's Folders, Tags and Documents as one value. A narrowed scope also holds where one click takes it back: `before: "all"` when it narrowed every Document, chosen; nothing when it narrowed the Mind's own. When two devices set it at once, one device's value wins whole, with its own way back, and no other key of the settings map is lost.
- **A check records where it looked.** The `claimCheck` mark's `scope` gains `chosen`, the scope searched when it was the Mind's own choice, so the card, the Word comment and the check record name it, and a check made in another scope than the Mind's now needs a re-check. An older version's editor would strip `chosen` and read such a check as made in the Mind's Folder, and it could write over the scope key without knowing it, so the content schema version is 26: an older version opens a Mind written since read-only. Nothing older is rewritten.
- **No table, no migration.** Nothing outside the Mind's Yjs document changes.

## Amendment: a change written over Blocks keeps the origins it replaced (2026-10-25, #1950)

A rewrite of an Answer's text is written over the Blocks it changes (#1873), and a revision with an instruction rewrites waiting Blocks in place, so they keep their ids and take the rewriting Answer's origin (`MIND_ORIGINS_FIELD`). Rejecting the change brought the text back but not the origin, so Use all on the earlier Answer missed its own text and wrote it a second time.

- **What the map holds.** A `replacedOrigins` map beside the Blocks (`MIND_REPLACED_ORIGINS_FIELD`) keeps, by the request whose change gave Blocks its origin, each such Block's earlier origin: the same reference to an Answer and the Question it answered as `origins` holds, and nothing of a device.
- **Rejected, the origin goes back.** Where rejecting takes that change out of a Block and nothing of it waits there any more, the Block's earlier origin goes back, in the decision's own step, so Undo and Redo take it back with the text, on the card and in the Mind.
- **Entries are kept for good.** An entry stays after the change is accepted, rejected or applied at once: History can bring back any earlier version of the Mind, with the change waiting again, and restoring it rejects that change, which needs the earlier origin. The map grows by one origin per Block a change was written over, the same size as that Block's own entry in `origins`, which also keeps entries for Blocks deleted since.
- **No schema version.** An older version keeps the map as it is and leaves `origins` as the change set them: its Reject keeps the rewriting Answer's origin, as before, and no text is lost. It raises no content schema version.
- **No table, no migration.** Nothing outside the Mind's Yjs document changes.

## Amendment: one sentence check keeps its parts (2026-10-28, #2002)

A sentence still has one `claimCheck` mark. Its ordered `parts` keep each part's UTF-16 character range, whether it is a fact or the writer's opinion, its result and its ordinary Citations. Parts don't overlap, with one exception: a number inside the writer's opinion is a fact part inside that opinion's range, so the opinion stays one part, counted and shown once, while its numbers are checked. Words a sort leaves out of every part that say more than a joining word (a time, place, scope or condition) join the fact beside them, or the opinion when no fact is beside them, so none is dropped unchecked and unlisted. A part's optional `decidingEvidence` indexes its deciding Citation in that array, or is null when none decides it; other checked quotes remain provenance without becoming deciding evidence. An omitted opinion has no verdict; a failed check remains Not checked. The sentence's result and singular evidence are projections of the parts, written together. Every factual part must be supported before the sentence is supported. A quantifier's coverage keeps its complete domain and checked member evidence separately; a domain list is never evidence that each member satisfies the claim.

Each part also owns its native figure and factual-remainder judgments, including the existing kept/pending state and original request, time and model metadata. The same canonical writer derives the parent figure inventory and result for Check again, Keep, footing and reload; an untouched sibling keeps its metadata. Omitted opinions never become a factual remainder. Core and editor share one exact projection from displayed model text to the original inline positions: Citation metadata is skipped, calculated atoms are expanded, and a part boundary inside an atom is refused. Original figure ids and locators are retained.

Part evidence receives ordinary Note-owned Citation ids in the Note result-write path. Unchanged owned receipts keep their ids, copies receive new ids, and ambiguous equal receipts are not merged. The existing Citation traversal, standing, sign-off record and Undo cover these receipts; no extra sign-off kind or hidden Citation node is introduced.

A sentence consisting only of omitted opinions has no mark. The Note keeps its exact words, Block, occurrence and part ranges in its settings instead. The same reader combines those entries with marked parts for Check and Verify. Changed words invalidate the saved ranges, and a new sort replaces them. Checking an opinion removes its unmarked entry and writes the same parts under the sentence's one mark, retaining the other parts' results.

## Amendment: a check reads a chosen Document or Folder whole (2026-10-30, #1554)

A not-found sentence can be checked against the whole text of one Document or Folder the User picks, rather than only the Passages ranked search supplies. The mark records the exact coverage so a partial read never claims that nothing exists in the unread part.

- **Content schema version 39** adds the `check-against-document` action, the `absence-unconfirmed` and `read-budget` reasons, and `read: { pages, of }` to the `claimCheck` mark. `pages` counts only pages every Passage of which reached the model in a request it answered, and `of` is the picked scope's total. An older version's editor would treat the mark as an ordinary check and drop its coverage, so it opens these Notes read-only. Older content is version 39 content as it is.
- **Part by part.** The read writes the sentence's one mark with its `parts` (#2002): a part already Supported or Contradicted keeps its result and Citations, and each other part is read against the pick. Asked about one part, it reads only that one. `read` is the coverage of the parts the result rests on.
- **The mark stays until the read ends.** Unlike an ordinary check, no "checking" mark is written first, so Stop or a crash leaves the previous mark. The result is written only if the sentence's mark is still the one the read started from and no newer read of it began; a sentence already being checked is refused.
- **An absence is judged window by window.** A part that says something is absent (#1443) is judged in each window the read already reads. A window that says the thing is there accuses the sentence, so its quote gets two looks, each asked only whether the quote states that very thing is there: when both say so, the part is Contradicted with that quote; a quote either look rejects leaves the window unjudged, so the part ends Not checked, never Supported. #1443's read of a short scope is unchanged. The part is Supported only when every window holds it absent and every page was read, its `readDocuments` naming each page. No request reads the whole pick at once, so there is no 40-page cap. Each window after the first starts with the last whole Passages of the one before, at least about 1,000 tokens of them, so a clause cut at a window's edge and up to about that long is whole in the next window.
- **The estimate is the requests the read sends, as the provider counts them.** About what it costs: for each part and window, the check's search, its verdict with the window's Passages, and the absence judgement, each counted with the instructions, prompt and Tools its Run builds, not a fixed overhead, and a quarter more requests, as Claude Haiku 5.5's reads sent. Their input is counted on this computer, never by a provider's counting service; each call is priced at its own prompt's tier as the meter prices it (#2287), and its tokens are shown as the provider may count them (`promptTokenRatio`). A window reaches the model once in each request: a check in a window is never asked to search again, and only its first search returns the window, a later one a line saying it has every Passage already. The most it may cost counts every request it may send, each writing all its call may (#2275's output limits): every call of the check's Run (eleven in all), each with the window and all the calls before it wrote, the requests a check may send after its Run (its evidence asked for twice, its quotes compared with the sentence), the judgement and the two looks at a quote, reserved as the meter reserves each request, at the tier of its prompt times the provider's ratio, with all its input written to the prompt cache where the provider bills that higher.
- **A read never spends more than its budget.** A read of sorted parts that costs about $0.50 or less starts without asking, held to its most or $0.50, whichever is less; any other asks "About $A, up to $B", where $B is twice $A, at least $0.50 and never more than the most it may cost, and is held to $B. The most counts every call at its output limit, far above what a read costs; a read that reaches its budget stops, and Continue asks again. The card's "up to" is always that budget. A sentence whose parts aren't sorted yet always asks, since how many parts it reads isn't known before a model call. The meter refuses, before it is sent, any request of the read (one Run, keyed by `model_requests.run_id`) whose reservation, with what the read's requests settled at and what its open ones reserved, would pass the budget, as it refuses one that would pass the monthly cap; a model with no price, or not billed per token, has none. Once one request is refused the read sends nothing more, and the parts not judged by then are Not checked with the `read-budget` reason. Its `detail` holds the budget, what the read's requests had settled at, one figure on every line it stopped, and for a part whether its read judges the part's absence, as the read's plan had it. The card says "Stopped after $Y; this read may spend up to $X" with Continue, which reads, and prices, only the parts that read stopped before judging, as they were planned: what is left never costs more than the whole. While the read runs, the sentence's card shows only its progress and Stop.
- **Every read has its plan.** `planDocumentCheck` sizes the read for its sentences, or its one part, and its pick, counting each window once for every part it will check, and the read names that plan. A newer plan in the Note stops a read already running, and a read whose plan is no longer the Note's latest sends nothing, checked again after consent and before each window. Check again and Accept all and check ask through the sentence's card as the first read did.
