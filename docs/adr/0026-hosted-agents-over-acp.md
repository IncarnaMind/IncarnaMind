# The assistant can run on the User's own agent, over the Agent Client Protocol

The User can use an agent harness they already have, such as Codex or Goose, for the assistant. IncarnaMind supplies the sources, the Citations and the checks; the agent supplies its loop, its own Tools and its model, on the User's own account. Everything the agent writes goes through the same checks as an Answer. Our Run engine stays the default: it led the agent-integration bake-off on document work (#1208), and most Users have no agent.

This records how (#353). ADR-0013's addendum of 2026-10-11 already decided that a hosted agent is a new kind of Run whose loop runs in the agent's process, that it gets IncarnaMind's MCP server, that its permission requests use our approval cards and that it starts in its most restrictive mode. This record amends that addendum where it said an outside agent's changes wait as Proposals (see ADR-0013's amendment of 2026-11-01). The build starts from the spike on the branch `spike/353-acp`, which drives a scripted ACP agent through the seams below with no network and no vendor binary, and ran each listed agent in the sandbox once by hand (`spikes/353-acp/agentsUnderSandbox.ts`). The spike's files named here are on that branch, not on `main`.

## The protocol and the library

- **ACP v1** (`protocolVersion` 1): JSON-RPC 2.0 over the agent's standard input and output, the client starting the agent as a child process ([transports](https://agentclientprotocol.com/protocol/v1/transports)). v2 is a public draft that removes modes, client file system and terminal; we move when it is stable and our agents speak it.
- **`@agentclientprotocol/sdk` 2.0.2**, pinned exactly: Apache-2.0, by the protocol's maintainers, with no dependencies (zod, which we ship, is its peer). Its stable v1 entry is 54 KB minified (13 KB gzipped), imports nothing from Node, and takes the agent as two web streams (`ndJsonStream`). 2.1.0 and later add an optional peer, `@modelcontextprotocol/server` ^2.4.0, for helpers we don't use; we move up once our MCP server package is there.
- **What ACP doesn't promise.** "Permission requests are advisory: the Agent performs its own operations", and "an Agent can act without asking" ([security](https://agentclientprotocol.com/protocol/v1/security)). Our checks hold for what reaches IncarnaMind: its MCP calls, its text, its edits through our tools, and the writes and commands it asks us for. What the agent can reach on its own is bounded by the OS sandbox (decision 2), not by ACP, and the consent says what is left.

## Decisions

### 1. A hosted Run

A hosted Run is one Question answered by the User's agent: one ACP prompt turn. It is neither a `RunEngine` nor an `AnswerEngine`, since both take our model and our Tools. It writes its Answer through the same writer an Answer uses, so storage, streaming, Stop, the steps, Citation marks and the Conversation are the Answer's. What it leaves out needs our model: our prompt, our Tool loop, the turn checks that ask the model again, quote retries, structured output and the price.

- **Started in `src/main`, behind an adapter.** The core gets an `AgentProcesses` adapter (`src/core/adapters.ts`): `start({ command, args, cwd, env })` resolves with an `AgentProcess` (its input and output as web streams, `exited`, `stderrTail()`, `stop()`). The desktop app implements it on the login shell's `ProcessLauncher`, inside the OS sandbox, so an agent is found as the User's terminal finds it, and each agent leads its own process group. The core's ACP client imports nothing from Node or Electron.
- **One process and one ACP session per Conversation,** while it is in use. Each Question is one prompt turn in it, so the agent keeps its own memory of the Conversation. The process stops after 10 minutes idle, when its window closes, when the User picks another model, and when the app quits. The next Question starts a new process and session, whose first prompt carries the Conversation's earlier turns.
- **Its working folder** is a new, empty folder in the system's temporary folder, made for the session and removed after it; never a Linked folder, the Output location or the User's home.
- **Stop** sends `session/cancel`, answers any request still waiting as cancelled (as ACP requires), and waits up to 5 s for the turn to end as `cancelled`. An agent that doesn't is stopped with every process it started, and the next Question starts it again.
- **An agent that exits halfway**, or closes its output, ends the turn once everything it wrote has been read: the Answer keeps the text that came, its Citations checked as usual, its running Tool calls marked failed, and one line with one action: "Codex stopped before it finished · Try again". The end of its error output goes to the log, never into the Answer.
- **Quitting** stops every agent process (input closed, 2 s grace, then the process tree); an Answer still streaming is stored as stopped. If the app crashes, the agent reads the end of its input, and its grant (decision 3) is gone with the app, so an agent that stays up can't reach IncarnaMind.
- **A host that can't start processes** (the mobile app, later) has no `AgentProcesses`, and the model menu has no "Your agents" group (portability rule 13). A Conversation that was on an agent says "Codex runs on your computer, not here" and offers the default model. Since the core's client takes two web streams, a later host can reach an agent elsewhere without changing it.
- **Windows:** not offered until the AppContainer helper (#2351, part 2) gives it a sandbox. For then: an npm-installed agent is a `.cmd` shim, which `cross-spawn` runs; our MCP server goes to the agent as the app's own absolute `.exe` path, since ACP asks agents to start MCP servers "without a shell"; Stop ends the process tree with `taskkill /T /F`; the SDK splits lines on LF or CRLF.

### 2. The agent runs in the OS sandbox

In their most restrictive start, the agents still read files and run some commands without asking (Codex's read-only mode, OpenCode's `read`, Gemini's `plan` mode). Unconfined, that would include IncarnaMind's data folder, which holds every Document's text whatever the Search scope and the Folder walls say. So every hosted agent, and every process it starts, runs in the OS sandbox IncarnaMind already uses for Skill scripts (`@anthropic-ai/sandbox-runtime`: Seatbelt on macOS, bubblewrap on Linux; ADR-0013):

- **It can't read** IncarnaMind's data folder, the User's Linked folders, the files of Documents added on their own, or the Output location. The User's Documents reach it only through our MCP tools.
- **It can write** its working folder and, of its own files, only its sign-in, sessions, cache and logs, which the agent list names per agent (such as `~/.codex/sessions`, never all of `~/.codex`). It can read its own folders; IncarnaMind never reads them itself. The rest of the disk stays as the User's account sees it, closed to writes.
- **It can never write its config, settings or hooks** (such as `~/.codex/config.toml` or `~/.qwen/settings.json`), not even inside a folder it may write: the profile denies them by name. Otherwise an agent steered by a Document could plant `approval_policy = "never"` or a hook there, which the User's own copy would later run from a terminal, outside any sandbox. (The spike's run still let each agent write its whole temporary home; the build narrows that and runs them again.)
- **It can reach** only its vendor's hosts, through sandbox-runtime's network proxy: fixed for Codex (OpenAI) and Gemini CLI (Google); for Goose and OpenCode, the hosts of the provider the User says they set it up with. When that provider runs on this computer, such as Ollama, the profile allows its one address (`localhost:11434` for Ollama, or the one the User gives) and nothing else local. Local mode still pauses every outside agent (decision 8).
- **And one local socket: the shim's.** #351's socket is `agents.sock` in the data folder, which the agent can't read. So a hosted session's shim reaches the app through a socket of its own, in the system's temporary folder, and the profile allows that one path and no other socket (Seatbelt's `network-outbound` to that Unix socket, sandbox-runtime's `allowUnixSockets`).
  - sandbox-runtime 0.0.79 reads the sockets a wrap allows, and the hosts its proxy lets through, from one configuration shared by everything that process wraps, Skill scripts included. So the agents' sandbox, its proxy and its socket rule run in a helper process of their own, never in the process that wraps Skill scripts.
- **It fails closed, by a probe.** Before any agent is offered, and again when the sandbox's library changes, IncarnaMind writes a file into its data folder and reads it with `cat` inside the agent's sandbox, beside a file in the agent's working folder, and connects to a socket other than the shim's from inside it. Agents are offered only if the first read fails, the second succeeds and the socket is refused (`agentSandboxHolds`). That `sandbox-exec` or bubblewrap exists proves nothing on its own.
- **Where the probe fails or the sandbox can't start,** no hosted agent is offered, and Settings says why in one line. That covers Windows until #2351 (part 2), and Linux for now: sandbox-runtime can allow Linux's Unix sockets only all or none, and all would open the User's other sockets (an SSH agent, Docker) to the agent. Linux is offered once the build shows the shim's connection with no other socket reachable.
- **The profile is fixed at launch.** A Linked folder, a Document or an Output location added later is only denied to an agent started after it, so the session restarts when one is added.
- **The grant (decision 3) limits only what IncarnaMind gives the agent;** the sandbox keeps it from IncarnaMind's data and the User's Documents. Neither stops it reading other files the User's account can read, or sending what it reads to its vendor; the consent says so.
- **Each agent is offered only once it has run under this profile,** since agents differ in what a sandbox breaks (one may need its own sandbox inside ours, or reach the network around the proxy). Each records what its restrictive start does without asking, measured by hand-testing that agent rather than taken from its docs, and the consent names it.
- **The keychain stays reachable.** The profile doesn't close macOS's keychain service to the agent, which it needs for its own sign-in. The item behind IncarnaMind's encrypted secrets file is protected there only by the system's own prompt, which names the program asking.

### 3. The session: IncarnaMind's MCP server, and what we offer the agent

- **Transport: stdio, through #351's shim.** Every ACP agent must take a stdio MCP server in `session/new` ([session setup](https://agentclientprotocol.com/protocol/v1/session-setup)). The server is the shim #351 ships: the app's own binary run as Node, talking to the running app over a local socket. Its command and two environment variables go in `session/new`'s `mcpServers`.
- **A run grant, not a pairing.** The session's server is admitted by a grant made for it: 256 random bits, held in memory only, never written to the database, the keychain, a file or a log, and gone when the session ends. A shim started with it later is refused as unpaired. Each call is checked as a pairing's is (#351): connecting agents on, Local mode off, consent in place. It reaches only the current Question's Search scope, as resolved when the Question was asked (its Folders, Tags and Documents, Folder walls kept).
  - It is not one of the User's secrets: it opens only that scope, for the session's life. It travels as any stdio MCP configuration does, to the agent and what it starts; ACP says agents "SHOULD NOT log or persist" such values, and one kept anyway is dead once the session ends. No API key, keychain item or token of the agent's vendor passes either way.
- **Citation tokens are bound to who minted them, and when.** A token counts only for the caller that minted it (a pairing, or a grant), in the Run (Question) that minted it, and while its Document is in that Run's Search scope. #351's access layer looks every token up by token and caller together, in `check_citations` and `show_citation` too, so the agent's own check and the Answer always agree. A token dies with its Run.
  - Each later prompt in the Conversation renews the earlier Citations still in the new Question's scope: their quotes are checked again and minted for the new Run. IncarnaMind itself translates an earlier Run's token the agent writes into the renewed one. After an idle restart, the earlier turns are sent with renewed tokens, so a true quote is never shown as Quote not found for outliving its session.
  - A token that is neither this Run's nor a renewed one is marked Quote not found.
- **Its Tools** are #351's reading Tools (`search`, `read_passages`, `cite`, `check_citations`, `list_minds`, `read_mind`) and IncarnaMind's write tools as an Answer in the assistant has them: the Notes' Tools (`edit_mind`, `add_to_mind`, `create_mind`) and the app's commands (`list_commands`, `run_command`, #1110), under the same policy and checks (decision 4). Not `ask`, which would run our model on the User's account inside their agent's turn, and not `show_citation`, which would move the window.
- **Client capabilities.** `fs.writeTextFile` and `terminal` are offered, so a file write or a command the agent asks IncarnaMind for comes to the approval card (decision 5) and is carried out only once allowed. `fs.readTextFile` is not: the agent reads the User's Documents through the MCP server. Terminal sign-in (`auth.terminal`) is declared off, and no elicitation is offered.
  - **A write** goes through IncarnaMind's file writing: one that would change a file in a Linked folder is refused before any card, since IncarnaMind never changes one (ADR-0010), and a new file there needs that folder's permission as well as the card.
  - **A command** runs through the `Executor` (ADR-0013) as a Skill script does: in the session's working folder, without the login shell's secret-looking variables, in the OS sandbox (no network, writes only in its folder). Its output, exit, kill and release are ACP's terminal methods.
- **The most restrictive mode, or no prompt.** Several agents start by asking about little or nothing (Codex's "Auto review", Goose's automatic approval, OpenCode's "allow" defaults). So each agent on our list names how it starts restricted: the launch setting it documents for that (`GOOSE_MODE`, `OPENCODE_PERMISSION`, Codex's approval policy) and the matching ACP mode. Both are applied, and the mode is checked after `session/new`, before the prompt. An agent that doesn't offer it gets no prompt, and the User reads "Qwen Code didn't offer its plan mode. Update Qwen Code · How". A mode that skips permissions is never chosen. An agent that switches during a turn to a mode that reduces the User's oversight, which ACP says it "SHOULD NOT" do without user action ([tool calls](https://agentclientprotocol.com/protocol/v1/tool-calls)), is stopped, with a line saying so.

### 4. Streaming, and the trust path

- `agent_message_chunk` text becomes the Answer's text, streamed as an Answer streams. `agent_thought_chunk` becomes its reasoning, in the steps, never in the Answer. `plan` is the Run's plan in the steps. The steps start "Codex worked for 12 s" (Codex 用了 12 秒).
- **The agent can't produce our markers.** An Answer marks a Citation as `[^n]` and a Calculated figure as `[=n]`, and the Markdown parser undoes escapes before markers are matched, so escaping the agent's text isn't enough. In a hosted Answer a Citation attaches only through a token minted for its Run, which the agent can't guess (`hostedAnswerText`):
  - every "[" the agent wrote that could start one of our markers, however escaped, gets an invisible word joiner after it, which no parsing removes;
  - only then does each token minted for this Run become the marker of its Citation;
  - the result is parsed as an Answer is, and must show no marker but those and no figure; if it does, every "[" is made inert, and if even that fails, the Answer keeps no marker at all;
  - it runs on the whole text so far, never chunk by chunk, so a marker split across chunks is caught too.

  Plain bracketed text such as "[Report, p. 4]" stays text.
- **A Citation is only what IncarnaMind minted and found again.** The agent cites with the tokens our `search` and `cite` hand it (`[cite:k3x9a2b7]`), whose text is held back while it streams. Each token is looked up as decision 3 binds it, then checked again against its Document as it is now (`recheck`), and only then becomes one of the Answer's Citations, recorded as an Answer's `cite` records them: found, Needs re-check if the Document changed since, or Quote not found. A token that is malformed, made up, or not this Run's is shown as Quote not found, never dropped and never green.
- **Figures.** A hosted Answer has Calculated figures only from IncarnaMind's own `calculate`, if the MCP server ever offers it; today it doesn't, so every number the agent works out itself is an Unchecked figure. A sentence without a Citation is uncited, as in any Answer. Nothing the agent says about its own checking changes a mark.
- **Third-party text from its start** (ADR-0013, #78). IncarnaMind can't see what the agent reads with its own tools, so a hosted Run counts as having read third-party text from its first step. The Note text it writes is recorded as third-party, so a later Run that reads it counts it so too. The AI use record and the Note's AI statement name the agent, with no model id, since IncarnaMind can't verify which model wrote.
- **Tool calls.** Calls to our MCP server are listed from our own exact record of them, not again from the agent's report. The agent's own Tool calls are listed with its title for them, marked as its own.
- **A Note edit applies at once, with Undo, as our engine's do** (ADR-0013, 2026-10-21). It comes only through IncarnaMind's write tools and is checked there like any other: the guard that holds back a change taking out most of the User's own text or rewriting words they typed since, and the Citation check above, with uncited sentences marked. A turn's changes are one step of Undo, and the Answer's card says what changed, from what the calls did. A reply that says it changed something no call changed gets the line that nothing was written, from that record alone: the agent's model can't be asked again.
- **Deletes wait on the approval card**, as they do for our engine (#1274): one card lists what would go, with Delete and Don't delete. Every other command follows the commands' one policy, unchanged: what never belongs to the assistant (keys, consent, Local mode, deleting for good and the rest) stays off for an agent too.

### 4a. Proposals stay for an outside agent on its own (#352)

This is only about an outside agent connected over MCP (#351) and acting on its own, while the User isn't in the assistant. Its changes to a Note arrive as Proposals and wait for the User (#352); a hosted Run never makes Proposals. For both to share one access layer, #352 exposes:

- `propose_changes` on pairings only: a run grant gets the write tools above instead, and a pairing never does;
- the caller's identity as the access layer gives it (a pairing or a run grant), with tokens looked up by caller (decision 3);
- a `ProposalRequest` (`source: "outside-agent"`) that records the agent's shown name and the pairing's id;
- the same Citation check of proposed text, with uncited sentences marked, proposed text recorded as third-party, and the AI use record naming the agent;
- the same path as every model's change to a Note (ADR-0003, amended for #2796): a part that can't be written, such as a paragraph rewritten without a <removed> the User typed there, refuses the whole change, and the agent is told why.

### 5. Everything outside our tools waits on the approval card

- **One card for what the agent would do outside IncarnaMind's tools:** its own Tools' requests (`session/request_permission`: file writes, commands, network calls), and the file writes (`fs/write_text_file`) and commands (`terminal/create`) it asks IncarnaMind to carry out. It is the approval card our engine uses, titled by what it would do ("Write a file", "Run code", "Open a web page", otherwise the agent's own title), with the usual "It would…" lines: "It would write “notes.md” in {folder}", "It would run `npm test` in {folder}", "It would open {site}". For the agent's own Tools it says "{Agent} runs it with its own tools. IncarnaMind can't see or undo it."
- **Allow once and Deny only.** No "For this run" and no "always", for now. We answer with the agent's `allow_once` or `reject_once` option, never `allow_always` or `reject_always`: an agent keeps those in its own settings, where IncarnaMind can't show or take them back ("The Agent owns remembered decisions", [tool calls](https://agentclientprotocol.com/protocol/v1/tool-calls)). An agent that offers no once option is answered as cancelled. A write or command the User denied is refused with an error the agent reads.
- **Calls to IncarnaMind's own server** that an agent asks about (Codex asks about MCP calls) come to the card like any other: the request's title is the agent's text, which can't prove which server a call goes to.
- **Every card says the turn may have read text the User didn't write** (decision 4), as #1274's cards do. It doesn't change what asks.
- **Denying** ends that step with a line in the steps ("Not allowed: Run code"); the agent decides how to go on. **Stop** withdraws a card still waiting, answered as cancelled.

### 6. Consent (ADR-0022)

- **Given where the User chooses the agent**: "Use for the assistant" in Settings › Agents and apps, or the agent in the model menu's "Your agents · Experimental" group the first time. That place says what goes to the agent, and says plainly what the agent can still do on its own:
  > Codex will get your Question, the note you're in, earlier turns of this chat, and what it asks IncarnaMind for in the Question's Search scope: Passages from your Documents, and your notes there. It sends them to its model under your Codex account. With its own tools it can also read other files on this computer and reach OpenAI, some of that without asking: {what runs without asking}. It can't read IncarnaMind's data or your Documents' files. Its own tools run outside IncarnaMind's checks and Undo.

  For Codex the line adds: "Codex's own sandbox is off here, and IncarnaMind's is in its place. Codex asks before it changes files or runs commands that write; it can read the files the sandbox allows, and run commands that only read, without asking."
- A new data flow, **"hosted-agents"**, one service per agent, listed on the Privacy page and revocable there. Revoking it stops a running session at once. It is asked again only if the flow starts sending a kind of data its line didn't name.
- **Background work never uses a hosted agent** and so never asks: checks, tagging, suggestions, Tasks and an outside agent's `ask` run on the User's model as before.

### 7. What we never do

- Show a vendor's sign-in, or run one: terminal sign-in is declared off, and an agent that isn't signed in gets a line telling the User to sign in to it where they set it up, with a link to its own page.
- Read an agent's tokens or settings: no file under an agent's own folders is opened by IncarnaMind, in code or in research, and a test checks it. Discovery looks only at the login shell's PATH. The agent's environment is the login shell's, as Connectors get it (ADR-0013); IncarnaMind adds only the agent's documented setting for its restrictive start, never a key or a token.
- Bundle a proprietary binary. We start what the User installed.
- Offer, set up, suggest, ask for or detect a plan route. The agent runs with what the User configured in it, which IncarnaMind can't see. The setup line says that some plans' terms forbid this use: Alibaba's, Z.ai's and Kimi's coding plans limit use to the tools they name.

### 8. The rest

- **Which agents.** The list, with sources, is in "Agents" below. Each entry in the agent list (the list Settings › Agents reads, ADR-0019) carries the command, its ACP entry, its restrictive start, what runs without asking there (measured by hand), what of its own it may write (sign-in, sessions, cache, logs) and what it never may (config, settings, hooks), its vendor's hosts for the sandbox, the lowest version that works, and its install page.
- **Discovery.** An agent on the list whose command is on the login shell's PATH is "found"; any other shows "not set up", and choosing it opens one line with a link to the agent's own install page. IncarnaMind installs and downloads nothing. The model menu and Settings show the agent's name and the version found ("Codex 0.166"), never how it signs in, which can't be known without reading the agent's settings.
- **Version checks.** When found, and again when its Test runs, the agent's `--version` is compared with the lowest version on the list, and `initialize` must answer protocol 1. Older: "Goose 1.40 is older than IncarnaMind needs (1.50 or later) · How to update". There is no upper bound; a newer version that breaks shows its plain error, and Test in Settings says "Answered in 4 s" or what went wrong.
- **The meter.** IncarnaMind can't price the agent's model and doesn't pay for it: the agent's own account does. A hosted Run is recorded with its time and no price, and doesn't count toward the Monthly cap, which only governs requests IncarnaMind sends. When the agent reports its session's cost (`usage_update.cost`), it is shown as the agent's figure ("$0.04, as Codex reports it"), never added to IncarnaMind's totals. The cost page lists hosted agents apart, by time and number of Questions.
- **Local mode** pauses every outside agent, hosted ones included (ADR-0013): IncarnaMind can't tell where an agent sends what it reads, and an agent's report of its own model is a claim we can't check. The line: "Local mode is on, so Codex can't be used: IncarnaMind can't tell where it sends what it reads · Turn off Local mode". This is stricter than #353's design, which blocked only agents with a cloud model.
- **Sync.** Nothing secret syncs: the run grant is never stored, and the agent's keys and sign-in stay in the agent, on that computer. A Conversation's chosen agent is the User's preference and syncs as a model choice does (`providerId` "agent:codex"); whether the agent is set up, its consent and its version belong to the device (portability rules 11 and 12). On a computer without it, the Conversation says so and offers the default model.

## Agents

Terms and ACP support were checked on 2026-10-31 against each agent's source and its vendor's terms. #353 (2026-10-13) named Codex, Goose, OpenCode, Cline and Kilo. "Runs without asking" is from each agent's docs and code until the hand tests replace it.

**Listed, each offered only once it runs under the profile** (decision 2). Each takes our MCP server over stdio. The spike ran each on 2026-11-01 on macOS, in the sandbox with a temporary home, a made-up API key and its vendor's hosts let through the proxy; only Qwen Code worked. Causes marked "likely" are inferred, not shown.

- **Codex** (the adapter `@agentclientprotocol/codex-acp` 2.5.0 over Codex 0.165.0, Apache-2.0, [config](https://github.com/agentclientprotocol/codex-acp)). Starts with its own sandbox off inside ours and its strictest approval policy ("Codex in our sandbox"), not its default "Auto review", which asks only about what it judges unsafe. Its docs name reading files, and web search from OpenAI's cache, as running without asking; to be measured with its sandbox off. Signs in with an API key, or its own ChatGPT sign-in under the condition below. **Not offered until it runs under the profile with a real User's sign-in**, a hand test on the owner's own account in the build: without a sign-in no turn ran, and its own sandbox can't start inside ours.
- **Goose** (native `goose acp` 1.57.0, Apache-2.0). Starts with `GOOSE_MODE=approve`, then mode `approve`: its default approves every call, and `chat` offers no Tools at all, ours included. Uses its own providers, set up with `goose configure`, which IncarnaMind doesn't see. **Not offered until it works:** its requests through the proxy failed, likely because its TLS doesn't trust the proxy.
- **OpenCode** (native `opencode acp`, MIT; 2.1.4 was run). Starts with `OPENCODE_PERMISSION` asking for every edit, command and fetch, then its `plan` agent: "Most permissions default to `allow`" ([docs](https://opencode.ai/docs/permissions/)), and `plan` alone doesn't restrict the shell. `read` still runs without asking (all but `.env` files), inside its working folder. Uses its own providers, on the User's keys. **Not offered until it works:** it exited at once, likely because its own local server can't listen in the sandbox.
- **Gemini CLI** (native `gemini --acp` 0.66.0, Apache-2.0), approved on a paid API key on 2026-11-01, never its Google sign-in (below). Starts in mode `plan` ("Read-only mode"), whose read-only Tools run without asking. **Not offered until it works:** it ignores the proxy.
- **Qwen Code** (`qwen --acp` 0.26.4, Apache-2.0). Starts in mode `plan`; its read-only Tools run without asking, to be measured. An API key is all it offers over ACP. **It ran:** it reached its vendor through the proxy, and the sandbox held back its other requests (models.dev, and telemetry to an Alibaba Cloud host).

**Codex in our sandbox.** macOS won't start Codex's own sandbox inside ours, so Codex runs with its own sandbox off, inside IncarnaMind's. Our sandbox is the wall, and its approvals are the door. That holds only on three conditions:

- **(a)** Codex is offered only after the probe (decision 2) proves the wall: reading a file in the data folder fails inside the sandbox, and a socket other than the shim's is refused.
- **(b)** Its approval policy stays the strictest it has, set at launch and checked as a restrictive mode is, so every file change and every command that writes asks through our approval card, with Allow once and Deny. Commands that only read still run without asking, inside our sandbox; the hand test records them and the consent says so. The build checks that codex-acp can set the approval policy apart from the sandbox mode.
- **(c)** Its consent says that Codex's own sandbox is off and IncarnaMind's is in its place (decision 6).

**Codex's ChatGPT sign-in, and its condition.** OpenAI: "If you've built a local or open-source application using Codex app-server authentication, you can continue using it… App-server authentication has never been permitted for commercial or hosted services" ([app-server](https://learn.chatgpt.com/docs/app-server)). So the route holds only while IncarnaMind is a local, open-source app with no paid service. A paid tier or a hosted version is checked against this first, and may close the route.

**Gemini CLI, on what it rests.** It is listed on a paid API key, approved on 2026-11-01. Antigravity CLI, to which Google is moving Gemini CLI's free and personal plans, stays on the Never list below.

- Google's transition notice (2026-05-19, [blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)): Gemini CLI stops serving Google AI Pro and Ultra and free use on June 18, 2026, and "Gemini CLI will remain accessible via paid Gemini and Gemini Enterprise Agent Platform API keys."
- Gemini CLI's terms ([`docs/resources/tos-privacy.md`](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/tos-privacy.md)) forbid "Directly accessing the services powering Gemini CLI … using third-party software, tools, or services". IncarnaMind never touches Gemini CLI's sign-in or the services behind it: it starts the unmodified CLI, which calls the Gemini API with the User's own key. With an API key, Gemini CLI is governed by the [Gemini API Terms of Service](https://ai.google.dev/gemini-api/terms), whose [paid services](https://ai.google.dev/gemini-api/terms#paid-services) terms apply to a paid key.

**Later:**

- **Kilo Code** (MIT, an OpenCode fork). Its terms changed hands on 2026-09-30 ([terms](https://kilo.ai/terms)), its npm release lags its source, and after one of its edits is allowed it also asks the client to write the file (`fs/write_text_file`) without checking that the client offered it, so one edit would bring two cards. Listed once a hand test shows how it behaves.
- **Cline** (Apache-2.0). Dropped from #353's list: `cline --acp` stores the `mcpServers` it is given and never connects them (`apps/cli/src/acp/acpAgent.ts`), so it can't reach IncarnaMind's Documents or mint a Citation. Listed if that changes.
- **Claude Code.** Stays on the MCP server (#351), as ADR-0013's addendum decided. Its ACP adapter runs on the Agent SDK, and "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" ([Anthropic](https://code.claude.com/docs/en/agent-sdk/overview)). If it is ever hosted, it is with the adapter's `--hide-claude-auth`, which refuses every turn a claude.ai plan would pay for.
- **Mistral Vibe** (Apache-2.0): Mistral's consumer terms forbid integrating its products with products offered to others without permission ([terms](https://legal.mistral.ai/terms/row-consumer-terms), clause (g)). **Kimi Code**: the registry still points at its archived CLI, and its plan is "for personal interactive use only". **GitHub Copilot CLI** and **Cursor**: proprietary, Copilot's ACP still a public preview.

**Never:** **Antigravity CLI**, whose terms make third-party access a breach ([terms](https://antigravity.google/terms)); **pi** (`pi-acp` stores the client's MCP servers without connecting them) and **OpenClaw** (its bridge rejects them).

**Plans.** IncarnaMind can't tell which key an agent uses, so it can't keep a coding plan out; it only never offers one (decision 7). The plans whose terms forbid this use: Alibaba's Coding Plan ("仅限在编程工具…中使用，禁止以 API 调用的形式用于自动化脚本、自定义应用程序后端…", [Bailian](https://help.aliyun.com/zh/model-studio/coding-plan)), Z.ai's GLM Coding Plan ("may only be used within officially supported tools and products", [Z.ai](https://docs.z.ai/devpack/usage-policy)) and Kimi's.

## Considered options

- **A `RunEngine`.** Rejected (ADR-0013's addendum): the model isn't ours, and a loop in another process can't honour the engine contract (our Tools, our gate, our window, our temperature).
- **An `AnswerEngine`.** Rejected: most of an `AnswerRequest` (prompt, quick model, turn checks, quote retries, structured output) needs our model; sharing the Answer's writer keeps what the User sees.
- **A process per Question.** Rejected: each Question would pay the agent's start, and the agent would forget the Conversation.
- **One process for the whole app.** Rejected: one crash would end every Conversation, and sessions with different Search scopes would share it.
- **Spawning agents from the core with `child_process`.** Rejected (portability rule 1): the core takes web streams, which a host without Node can give.
- **The agent unconfined, relying on the grant and the consent.** Rejected (decision 2): agents read files without asking, and the data folder holds every Document's text.
- **Denying the agent the whole home folder,** as Skill scripts are. Rejected: agents keep their settings, sessions and project tools there, and would break in ways each release changes; denying IncarnaMind's data and the User's Documents keeps the consent's promise.
- **On Linux, allowing every Unix socket.** Not now: it would open the User's other sockets to the agent.
- **A localhost HTTP MCP server with a bearer token.** Rejected, as in ADR-0013's addendum: a web page can try the port, and HTTP is optional for agents (`mcpCapabilities.http`).
- **MCP over the ACP connection itself** (`"type": "acp"`, [RFD](https://agentclientprotocol.com/rfds/mcp-over-acp)): no shim, socket or grant. Not now: a draft, gated on `mcpCapabilities.acp`, which no agent we list advertises; we move to it when it is stable and they do, which also ends the Linux socket question.
- **A standing pairing (#351) for the agent.** Rejected: it outlives the Question and has its own Folders, so it would reach beyond the Question's Search scope and leave a credential behind.
- **Tokens keyed to the Conversation.** Rejected: a token would pass under a later Question's narrower Search scope; renewing earlier Citations keeps them true.
- **The hosted assistant's Note edits as Proposals** (#352's mechanism). Rejected: in the assistant a change applies at once with one Undo (ADR-0013, 2026-10-21), the same request shouldn't behave differently by model, and the checks that make that safe run in IncarnaMind's write tools whichever loop calls them.
- **No `fs` and no `terminal`.** Rejected: agents would use their own Tools, whose requests come to the card anyway, while what IncarnaMind carries out keeps ADR-0010's rule and the `Executor`. Revisited with v2, which removes both.
- **"For this run", and the agent's `allow_always`.** Not now: one click would cover later calls the User hasn't seen, and `allow_always` lives in the agent's settings, which IncarnaMind can't show or revoke.
- **Downloading or bundling an agent's ACP adapter.** Rejected for now: it is code we would vouch for and keep current; the User installs Codex's with Codex.
- **Counting the agent's reported cost toward the Monthly cap.** Rejected: the cap refuses a request before it is sent, and a figure reported after the fact can't stop anything.
- **Letting Local mode admit agents that say their model is local.** Not now: the agent's word is all we would have; a later amendment can, given a way to tell.

## Consequences

- The build adds `@agentclientprotocol/sdk` 2.0.2, pinned exactly (Apache-2.0, small, maintained by the protocol's own maintainers), the dependency ADR-0013's addendum named. The core imports only its stable v1 entry. This record adds no code or dependency; the spike branch has both.
- `src/core/adapters.ts` gains `AgentProcesses`, `AgentProcess` and `AgentProgram`; the desktop app supplies them (`src/main/agentProcesses.ts`), each agent wrapped by `OsSandbox.confineAgent` (`src/main/sandbox.ts`) after `agentSandboxHolds` passes.
- The agents' helper process (decision 2) starts sandbox-runtime's network proxy, which the Skill scripts' sandbox doesn't start (it would take the app's SIGINT and SIGTERM), and keeps the app's own quit handling. #351's `agents.sock` stays where it is for outside agents.
- `src/core/agents/` gains run grants beside pairings, and the hosted Run. #351's access layer takes either, and looks tokens up by token and caller everywhere.
- **`agent_citations`, a migration** (the next free number at merge, per `AGENTS.md`): the table gains `run_id` (the Run that minted a token; null for a pairing's), and an index on `(pairing_id, token)`. A Run's rows are soft-deleted when it ends, once its Answer holds its Citations. At start, rows whose `pairing_id` is no live pairing (every grant's, after a quit or a crash) are soft-deleted too. Soft deletes and timestamps as ADR-0003 asks.
- The approval requests gain a kind for what an agent would do outside our tools (its own Tool, a file write, a command), with Allow once and Deny and no policy. Deletes use #1274's card as they are.
- A data flow, "hosted-agents", on the Privacy page and in `docs/privacy.md` and `docs/where-your-data-goes.md`.
- The agent list (ADR-0019) gains the hosted fields above. An agent moves on or off the list with a one-line change, when its terms, its ACP support or its hand test change.
- ADR-0013 is amended (2026-11-01): the addendum's rejected option "Let agents write to Minds directly" now holds only for an outside agent on its own; the hosted assistant edits in place with Undo. Its line that outside agents aren't offered the commands no longer holds for a hosted Run.
- #353's design shows the agent's name and version, not its sign-in, and its acceptance criteria follow this record once it is accepted (no Proposals, no "For this run").
- CONTEXT.md gains a term for the User's agent running the assistant when this is built.
- **Before release**, each listed agent is tried by hand with the cheapest model that answers (`AGENTS.md`), its "runs without asking" filled in from that, and its terms read again.

## Addendum, 2026-11-20 · preparing a Meeting summary

A device can prepare a read-only Meeting summary in its selected Codex or Claude Code client when the User explicitly enables automatic summaries for that pairing. The installed client uses its own authentication and billing. The core checks access to both the Meeting Note and its Transcript before sending confirmed lines and the previous summary, including its displayed decisions and action items. Tool use is disabled for this operation. The User can revoke it, and the manual Ask your AI handoff remains available. This decision applies to the meeting summary operation. [Claude Code product terms](https://code.claude.com/docs/en/legal-and-compliance#can-customers-offer-claude-code-in-their-products)

## An explicit Call Help question in a live Meeting (2026-11-21)

The User can select a connected Claude Code or Codex separately for Call Help. Pressing a help button or sending a question in the panel authorizes a tool-free request on that pairing. The core selects confirmed speech from the latest ten minutes of this Meeting's Transcript, within the pairing's current access. The request includes the question and numbered speech. It has no access to the Note, other Documents or tools. Changing the selection, ending the Meeting or revoking access cancels an outstanding request. The panel binds returned source numbers to checked, timed Transcript Citations, and lets the User read or open the quoted words. If the Transcript does not support a reply, the panel says so. The automatic summary has its own setting.
