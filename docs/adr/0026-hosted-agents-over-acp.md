# The assistant can run on the User's own agent, over the Agent Client Protocol

The User can use an agent harness they already have, such as Codex or Goose, for the assistant. IncarnaMind supplies the sources, the Citations and the checks; the agent supplies its loop, its own Tools and its model, on the User's own account. Everything the agent writes goes through the same checks as an Answer. Our Run engine stays the default: it led the agent-integration bake-off on document work (#1208), and most Users have no agent.

This records how (#353), under ADR-0013's addendum of 2026-10-11, which already decided that a hosted agent is a new kind of Run whose loop runs in the agent's process, that it gets IncarnaMind's MCP server, that its permission requests use our approval cards and that it starts in its most restrictive mode. It amends that addendum where it said an outside agent's changes wait as Proposals (see ADR-0013's amendment of 2026-11-01). A spike on this branch drives a scripted ACP agent through the seams below with no network and no vendor binary (`src/core/agents/hosted.ts`, `src/main/agentProcesses.ts`, `src/main/sandbox.ts`, and their tests `tests/main/hostedAgent.test.ts`, `tests/main/agentSandbox.test.ts` and `tests/core/hostedMarkers.test.ts`), and runs each listed agent in the sandbox once by hand (`spikes/353-acp/agentsUnderSandbox.ts`).

## The protocol and the library

- **ACP v1** (`protocolVersion` 1): JSON-RPC 2.0 over the agent's standard input and output, the client starting the agent as a child process ([transports](https://agentclientprotocol.com/protocol/v1/transports)). v2 is a public draft that removes modes, client file system and terminal; we build on v1 and move when v2 is stable and our agents speak it.
- **`@agentclientprotocol/sdk` 2.0.2**, pinned exactly: Apache-2.0, by the protocol's maintainers, with no dependencies (zod, which we ship, is its peer). The stable v1 entry the core imports is 54 KB minified (13 KB gzipped) and imports nothing from Node; it takes the agent as two web streams (`ndJsonStream`). 2.0.0 replaced `ClientSideConnection` with the `client()` builder the spike uses, and stopped publishing its example agent, so the spike's scripted agent is our own (`tests/fixtures/acp-agent.mjs`). 2.1.0 and later add an optional peer of `@modelcontextprotocol/server` ^2.4.0 for helpers we don't use; we move up once our MCP server package is there.
- **What ACP doesn't promise.** "Permission requests are advisory: the Agent performs its own operations", and "an Agent can act without asking" ([security](https://agentclientprotocol.com/protocol/v1/security)). Our checks hold for what reaches IncarnaMind: its MCP calls, its text, its edits through our tools, and the writes and commands it asks us for. What the agent can reach on its own is bounded by the OS sandbox (decision 2), not by ACP, and the consent says what is left.

## Decisions

### 1. A hosted Run

A hosted Run is one Question answered by the User's agent: one ACP prompt turn. It is neither a `RunEngine` nor an `AnswerEngine`, since both take our model and our Tools. It writes its Answer through the same writer an Answer uses, so storage, streaming, Stop, the steps, Citation marks and the Conversation are the Answer's. What it leaves out needs our model: our prompt, our Tool loop, the turn checks that ask the model again, quote retries, structured output and the price.

- **Started in `src/main`, behind an adapter.** The core gets an `AgentProcesses` adapter (`src/core/adapters.ts`): `start({ command, args, cwd, env })` resolves with an `AgentProcess`: its input and output as web streams, `exited`, `stderrTail()` and `stop()`. The desktop app implements it on the login shell's `ProcessLauncher` (`src/main/agentProcesses.ts`), inside the OS sandbox (decision 2), so an agent is found as the User's terminal finds it, and each agent leads its own process group. The core's ACP client (`src/core/agents/hosted.ts`) imports nothing from Node or Electron.
- **One process and one ACP session per Conversation,** while it is in use. Each Question is one prompt turn in it, so the agent keeps its own memory of the Conversation. The process stops after 10 minutes idle, when its window closes, when the User picks another model, and when the app quits. The next Question starts a new process and session, whose first prompt carries the Conversation's earlier turns, as an Answer's Question context does.
- **Its working folder** is a new, empty folder in the system's temporary folder, made for the session and removed after it. Never a Linked folder, the Output location or the User's home: the agent's own Tools start from it.
- **Stop** sends `session/cancel`, answers any request still waiting as cancelled (as ACP requires), and waits up to 5 s for the turn to end as `cancelled`. An agent that doesn't is stopped with every process it started, and the next Question starts it again.
- **An agent that exits halfway**, or closes its output, ends the turn once everything it wrote has been read: the Answer keeps the text that came, its Citations checked as usual, its running Tool calls marked failed, and one line with one action: "Codex stopped before it finished · Try again". The end of its error output goes to the log, never into the Answer.
- **Quitting** stops every agent process (input closed, 2 s grace, then the process tree); an Answer still streaming is stored as stopped, as any Answer is. If the app itself crashes, the agent's input closes, so it reads the end of its input, and its grant (decision 3) is gone with the app: an agent that stays up can't reach IncarnaMind.
- **A host that can't start processes** (the mobile app, later) has no `AgentProcesses`, and the model menu has no "Your agents" group (portability rule 13). A Conversation that was on an agent says "Codex runs on your computer, not here" and offers the default model. Because the core's client takes two web streams, a later host can reach an agent elsewhere (a WebSocket to the User's computer) without changing it.
- **Windows:** not offered until the AppContainer helper (#2351, part 2) gives it a sandbox (decision 2). For then: an npm-installed agent is a `.cmd` shim, which `cross-spawn` runs; our MCP server goes to the agent as the app's own absolute `.exe` path, since ACP asks agents to start MCP servers "without a shell"; Stop ends the process tree with `taskkill /T /F`; the SDK splits lines on LF or CRLF.

### 2. The agent runs in the OS sandbox

In their most restrictive start, the agents still read files and run some commands without asking: Codex's docs say that in read-only mode it "can read files and run commands within the read-only sandbox", OpenCode's `read` is allowed by default, and Gemini's `plan` mode runs its read-only Tools. Unconfined, that would include IncarnaMind's data folder, which holds every Document's text whatever the Search scope and the Folder walls say. So every hosted agent, and every process it starts, runs in the OS sandbox IncarnaMind already uses for Skill scripts (`@anthropic-ai/sandbox-runtime`: Seatbelt on macOS, bubblewrap on Linux; ADR-0013):

- **It can't read** IncarnaMind's data folder, the User's Linked folders, the files of Documents added on their own, or the Output location. The User's Documents reach it only through our MCP tools.
- **It can write** its working folder and, of its own files, only its sign-in, sessions, cache and logs, which the agent list names per agent (such as `~/.codex/sessions`, never all of `~/.codex`). It can read its own folders. IncarnaMind lets the agent reach them; it never reads them itself. The rest of the disk stays as the User's account sees it, and closed to writes.
- **It can never write its config, settings or hooks** (such as `~/.codex/config.toml` or `~/.qwen/settings.json`), not even inside a folder it may write: the profile denies them by name. Otherwise an agent steered by a Document could plant `approval_policy = "never"` or a hook there, which the User's own copy would run later from a terminal, outside any sandbox. The spike tests that a write to the settings file is refused and a write to the cache allowed (`tests/main/agentSandbox.test.ts`). The spike's run of each agent (below) still let it write its whole temporary home; the build narrows that and runs them again.
- **It can reach** only its vendor's hosts, through sandbox-runtime's network proxy: fixed for Codex (OpenAI) and Gemini CLI (Google); for Goose and OpenCode, the hosts of the provider the User says they set it up with. When that provider runs on this computer, such as Ollama, the profile allows its one address (`localhost:11434` for Ollama, or the one the User gives) and nothing else local. Local mode still pauses every outside agent (decision 8), since IncarnaMind can't confirm which model the agent uses.
- **And one local socket: the shim's.** #351's socket is `agents.sock` in the data folder, which the agent can't read, so a hosted session's shim reaches the app through a socket of its own outside the data folder, in the system's temporary folder, and the profile allows that one path and no other socket (Seatbelt's `network-outbound` to that Unix socket, sandbox-runtime's `allowUnixSockets`). The spike proves it end to end: the scripted agent, in the sandbox with the data folder denied, starts the real shim, which reaches a real core through the allowed socket and lists its Tools; with another path allowed instead, the same shim answers "IncarnaMind isn't open" (`tests/main/agentSandbox.test.ts`).
  - sandbox-runtime 0.0.79 reads the sockets a wrap allows, and the proxy reads the hosts it lets through, from one configuration shared by everything that process wraps, Skill scripts included. So the agents' sandbox, its proxy and its socket rule run in a helper process of their own, never in the process that wraps Skill scripts. (The spike sets the socket rule for one wrap and puts it back at once, which is enough for its tests and no more.)
- **It fails closed, by a probe.** Before any agent is offered, and again when the sandbox's library changes, IncarnaMind writes a file into its data folder and reads it with `cat` inside the agent's sandbox, beside a file in the agent's working folder, and connects to a socket other than the shim's from inside it. Agents are offered only if the first read fails, the second succeeds and the socket is refused. The spike's `agentSandboxHolds` makes the two reads, tested both ways; the refused socket is shown in `tests/main/agentSandbox.test.ts`, and the build adds it to the probe. That `sandbox-exec` or bubblewrap exists proves nothing on its own. Where the probe fails or the sandbox can't start as above, no hosted agent is offered, and Settings says why in one line. That covers Windows until #2351 (part 2), and Linux for now: sandbox-runtime can allow Linux's Unix sockets only all or none, and all would open the User's other sockets (an SSH agent, Docker) to the agent. Linux is offered once the build shows the shim's connection with no other socket reachable.
- **The profile is fixed at launch.** A Linked folder, a Document or an Output location added later is only denied to an agent started after it, so the session restarts when one is added.
- **The grant (decision 3) limits only what IncarnaMind gives the agent.** The sandbox is what keeps it from IncarnaMind's data and the User's Documents. Neither stops it reading other files the User's account can read, or sending what it reads to its vendor; the consent says so.
- **What runs without asking.** Each agent on the list records what its restrictive start does without asking, measured by hand-testing that agent rather than taken from its docs, and the consent names it.
- **Each agent is offered only once it has run under this profile.** Agents differ in what a sandbox breaks: one may need its own sandbox inside ours, or reach the network around the proxy. "Agents" below says what each did in the spike's run (`spikes/353-acp/agentsUnderSandbox.ts`), and one that wasn't run, or didn't work, isn't offered until it does.
- **The keychain stays reachable.** The profile doesn't close macOS's keychain service to the agent, which it needs for its own sign-in. The item behind IncarnaMind's encrypted secrets file is protected there only by the system's own prompt, which names the program asking.

### 3. The session: IncarnaMind's MCP server, and what we offer the agent

- **Transport: stdio, through #351's shim.** Every ACP agent must take a stdio MCP server in `session/new` ([session setup](https://agentclientprotocol.com/protocol/v1/session-setup)). The server is the shim #351 ships: the app's own binary run as Node, which talks to the running app over a local socket. Its command and two environment variables go in `session/new`'s `mcpServers`.
- **A run grant, not a pairing.** The session's server is admitted by a grant made for it: 256 random bits, held in memory only, never written to the database, the keychain, a file or a log, and gone when the session ends. A shim started with it later is refused as unpaired. Each call is checked as a pairing's is (#351): connecting agents on, Local mode off, consent in place. It reaches only the current Question's Search scope, as resolved when the Question was asked (its Folders, Tags and Documents, Folder walls kept).
  - It is not one of the User's secrets: it opens nothing but that scope for the life of the session. It travels as any stdio MCP configuration does, to the agent and to what the agent starts; ACP calls such `env` values credentials that agents "SHOULD NOT log or persist" ([session setup](https://agentclientprotocol.com/protocol/v1/session-setup)), and one an agent keeps anyway is dead once the session ends. No API key, keychain item or token of the agent's vendor passes either way.
- **Citation tokens are bound to who minted them, and when.** A token counts only for the caller that minted it (a pairing, or a grant), in the Run (Question) that minted it, and while its Document is in that Run's Search scope. #351's access layer looks every token up by token and caller together, in `check_citations` and `show_citation` too, so the agent's own check and the Answer always agree. A token dies with its Run. Each later prompt in the Conversation renews the earlier Citations still in the new Question's scope: their quotes are checked again and minted for the new Run. When the agent writes an earlier Run's token, IncarnaMind translates it into the renewed one itself, and never relies on the agent to swap them. After an idle restart, the earlier turns are sent with renewed tokens in place, so a true quote is never shown as Quote not found for having outlived its session. A token that is neither this Run's nor a renewed one is marked Quote not found.
- **Its Tools** are #351's reading Tools (`search`, `read_passages`, `cite`, `check_citations`, `list_minds`, `read_mind`) and IncarnaMind's write tools as an Answer in the assistant has them: the Notes' Tools (`edit_mind`, `add_to_mind`, `create_mind`) and the app's commands (`list_commands`, `run_command`, #1110), under the same policy and checks (decision 4). Not `ask`, which would run our model on the User's account inside their agent's turn, and not `show_citation`, which would move the window.
- **Client capabilities.** `fs.writeTextFile` and `terminal` are offered, so that a file write or a command the agent asks IncarnaMind for comes to the approval card (decision 5) and is carried out by IncarnaMind only once allowed. `fs.readTextFile` is not: the agent reads the User's Documents through the MCP server. Terminal sign-in (`auth.terminal`) is declared off, and no elicitation is offered.
  - **A write** goes through IncarnaMind's file writing: one that would change a file in a Linked folder is refused before any card, since IncarnaMind never changes one (ADR-0010), and a new file there needs that folder's permission as well as the card.
  - **A command** runs through the `Executor` (ADR-0013) as a Skill script does: in the session's working folder, without the login shell's secret-looking variables, in the OS sandbox (no network, writes only in its folder). Its output, exit, kill and release are ACP's terminal methods.
- **The most restrictive mode, or no prompt.** Several agents start by asking about little or nothing (Codex's "Auto review", Goose's automatic approval, OpenCode's "allow" defaults), so each agent on our list names how it starts restricted: the setting it documents for that at launch (`GOOSE_MODE`, `OPENCODE_PERMISSION`, Codex's approval policy) and the ACP mode that matches. Both are applied, and the mode is checked after `session/new`, before the prompt. An agent that doesn't offer it gets no prompt, and the User reads "Qwen Code didn't offer its plan mode. Update Qwen Code · How". A mode that skips permissions is never chosen. ACP says agents "SHOULD NOT switch to a mode or configuration that reduces user oversight without user action" ([tool calls](https://agentclientprotocol.com/protocol/v1/tool-calls)); one that does during a turn is stopped, with a line saying so.

### 4. Streaming, and the trust path

- `agent_message_chunk` text becomes the Answer's text, streamed as an Answer streams. `agent_thought_chunk` becomes its reasoning, in the steps, never in the Answer. `plan` is the Run's plan in the steps. The steps start "Codex worked for 12 s" (Codex 用了 12 秒).
- **The agent can't produce our markers.** An Answer marks a Citation as `[^n]` and a Calculated figure as `[=n]`, and the Markdown parser undoes escapes before markers are matched, so escaping the agent's text isn't enough. In a hosted Answer a Citation attaches only through a token minted for its Run, which the agent can't guess (`hostedAnswerText`):
  - every "[" the agent wrote that could start one of our markers, however escaped, gets an invisible word joiner after it, which no parsing removes;
  - only then does each token minted for this Run become the marker of its Citation;
  - the result is parsed as an Answer is, and must show no marker but those and no figure; if it does, every "[" is made inert, and if even that fails, the Answer keeps no marker at all;
  - it runs on the whole text so far, never chunk by chunk, so a marker split across chunks is caught too.
  The spike tests it through `answerBlocks`, the path every Answer is shown by: the agent's `[^1]` and `[=1]` plain, in a block quote, in bold, inside a link, escaped by the agent, as a footnote and split across chunks, in English and Chinese, beside a real token for Citation 1 (`tests/core/hostedMarkers.test.ts`). Plain bracketed text such as "[Report, p. 4]" stays text.
- **A Citation is only what IncarnaMind minted and found again.** The agent cites with the tokens our `search` and `cite` hand it (`[cite:k3x9a2b7]`). A token's text is held back while it streams. Each token is looked up as decision 3 binds it, then checked again against its Document as it is now (`recheck`), and only then becomes one of the Answer's Citations, recorded as an Answer's `cite` records them: found, Needs re-check if the Document changed since, or Quote not found. A token that is malformed, made up, or not this Run's is shown as Quote not found, never dropped and never green.
- **Figures.** A hosted Answer has Calculated figures only from IncarnaMind's own `calculate`, if the MCP server ever offers it; today it doesn't, so every number the agent works out itself is an Unchecked figure. A sentence without a Citation is uncited, as in any Answer. Nothing the agent says about its own checking changes a mark.
- **Third-party text from its start** (ADR-0013, #78). IncarnaMind can't see what the agent reads with its own tools, so a hosted Run counts as having read third-party text from its first step. The Note text it writes is recorded as third-party, as an Answer's is after reading some, so a later Run that reads it counts it so too. The AI use record and the Note's AI statement name the agent, with no model id, since IncarnaMind can't verify which model wrote.
- **Tool calls.** Calls to our MCP server are listed from our own record of them, which is exact; the agent's report of the same calls is not shown twice. The agent's own Tool calls are listed with its title for them, marked as its own.
- **A Note edit applies at once, with Undo, as our engine's do** (ADR-0013, 2026-10-21). It comes only through IncarnaMind's write tools, and is checked there like any other: the guard that holds back a change taking out most of the User's own text or rewriting words they typed since, and the Citation check above on the text it writes, with uncited sentences marked. A turn's changes are one step of Undo, and the Answer's card says what changed, from what the calls did. A reply that says it changed something no call changed gets the line that nothing was written, from that record alone: the agent's model can't be asked again.
- **Deletes wait on the approval card**, as they do for our engine (#1274): one card lists what would go, with Delete and Don't delete. Every other command follows the commands' one policy, unchanged: what never belongs to the assistant (keys, consent, Local mode, deleting for good and the rest) stays off for an agent too.

### 4a. Proposals stay for an outside agent on its own (#352)

This section is only about an outside agent connected over MCP (#351) and acting on its own, while the User isn't in the assistant. Its changes to a Note arrive as Proposals and wait for the User (#352); a hosted Run never makes Proposals. For both to share one access layer, #352 exposes:
- `propose_changes` on pairings only: a run grant gets the write tools above instead, and a pairing never does;
- the caller's identity as the access layer gives it (a pairing or a run grant), with tokens looked up by caller (decision 3);
- a `ProposalRequest` (`source: "outside-agent"`) that records the agent's shown name and the pairing's id;
- the same Citation check of proposed text, with uncited sentences marked, proposed text recorded as third-party, and the AI use record naming the agent.

### 5. Everything outside our tools waits on the approval card

- **One card for what the agent would do outside IncarnaMind's tools:** its own Tools' requests (`session/request_permission`: file writes, commands, network calls), and the file writes (`fs/write_text_file`) and commands (`terminal/create`) it asks IncarnaMind to carry out. The card is the approval card our engine uses, titled by what it would do ("Write a file", "Run code", "Open a web page", otherwise the agent's own title), with the usual "It would…" lines under it: "It would write “notes.md” in {folder}", "It would run `npm test` in {folder}", "It would open {site}". For the agent's own Tools it says "{Agent} runs it with its own tools. IncarnaMind can't see or undo it."
- **Allow once and Deny only.** No "For this run" and no "always", for now. We answer the agent's request with its `allow_once` or `reject_once` option, and never choose `allow_always` or `reject_always`: an agent keeps those in its own settings, where IncarnaMind can't show or take them back ("The Agent owns remembered decisions", [tool calls](https://agentclientprotocol.com/protocol/v1/tool-calls)). An agent that offers no once option is answered as cancelled. A write or command IncarnaMind was asked to carry out and the User denied is refused with an error the agent reads.
- **Calls to IncarnaMind's own server** that an agent asks about (Codex asks about MCP calls) come to the card like any other: the request's title is the agent's text, which can't prove which server a call goes to.
- **Every card says the turn may have read text the User didn't write** (decision 4), as #1274's cards do. It doesn't change what asks.
- **Denying** ends that step with a line in the steps ("Not allowed: Run code"); the agent decides how to go on. **Stop** withdraws a card still waiting, answered as cancelled.
- The spike tests that each of the agent's own calls asks and is answered once, never with the agent's always options; that Deny answers reject-once; that a file write and a command happen only once allowed, and not when denied; and that Stop withdraws a waiting request.

### 6. Consent (ADR-0022)

- **Given where the User chooses the agent**: "Use for the assistant" in Settings › Agents and apps, or the agent in the model menu's "Your agents · Experimental" group the first time. That place says what goes to the agent, and says plainly what the agent can still do on its own:
  > Codex will get your Question, the note you're in, earlier turns of this chat, and what it asks IncarnaMind for in the Question's Search scope: Passages from your Documents, and your notes there. It sends them to its model under your Codex account. With its own tools it can also read other files on this computer and reach OpenAI, some of that without asking: {what runs without asking}. It can't read IncarnaMind's data or your Documents' files. Its own tools run outside IncarnaMind's checks and Undo.

  For Codex the line adds: "Codex's own sandbox is off here, and IncarnaMind's is in its place. Codex asks before it changes files or runs commands that write; it can read the files the sandbox allows, and run commands that only read, without asking."
- A new data flow, **"hosted-agents"**, one service per agent, listed on the Privacy page and revocable there. Revoking it stops a running session at once. It is asked again only if the flow starts sending a kind of data its line didn't name.
- **Background work never uses a hosted agent** and so never asks: checks, tagging, suggestions, Tasks and an outside agent's `ask` run on the User's model as before.

### 7. What we never do

- Show a vendor's sign-in, or run one: terminal sign-in is declared off, and an agent that isn't signed in gets a line telling the User to sign in to it where they set it up, with a link to its own page.
- Read an agent's tokens or settings: no file under an agent's own folders is opened by IncarnaMind, in code or in research, and a test checks it. Discovery looks only at the login shell's PATH. The agent's environment is the login shell's, as Connectors get it (ADR-0013); IncarnaMind adds only the agent's documented setting for its restrictive start, never a key or a token.
- Bundle a proprietary binary. We start what the User installed.
- Offer, set up, suggest, ask for or detect a plan route. The agent runs with what the User configured in it, which IncarnaMind can't see. The setup line says that some plans' terms forbid this use: Alibaba's, Z.ai's and Kimi's coding plans limit use to the tools they name.

### 8. The rest

- **Which agents.** The list, with sources, is in "Agents" below. Each entry in the agent list (the same list Settings › Agents reads, ADR-0019) carries the command, its ACP entry, its restrictive start, what runs without asking there (measured by hand), what of its own it may write (sign-in, sessions, cache, logs) and what it never may (config, settings, hooks), its vendor's hosts for the sandbox, the lowest version that works, and its install page.
- **Discovery.** An agent on the list whose command is on the login shell's PATH is "found"; any other shows "not set up", and choosing it opens one line with a link to the agent's own install page. Nothing is installed or downloaded by IncarnaMind. The model menu and Settings show the agent's name and the version found ("Codex 0.166"), never how it signs in: #353's boards showed "Codex · your ChatGPT sign-in", which can't be known without reading the agent's settings.
- **Version checks.** When found, and again when its Test runs, the agent's `--version` is read and compared with the lowest version on the list; `initialize` must answer protocol 1. Older: "Goose 1.40 is older than IncarnaMind needs (1.50 or later) · How to update". There is no upper bound; a newer version that breaks shows its plain error, and Test in Settings says "Answered in 4 s" or what went wrong.
- **The meter.** IncarnaMind can't price the agent's model and doesn't pay for it: the agent's own account does. A hosted Run is recorded with its time and no price, and doesn't count toward the Monthly cap, which only governs requests IncarnaMind sends. The Answer shows "Codex worked for 12 s"; when the agent reports its session's cost (`usage_update.cost`), it is shown as the agent's figure ("$0.04, as Codex reports it"), never added to IncarnaMind's totals. The cost page lists hosted agents apart, by time and number of Questions.
- **Local mode** pauses every outside agent, hosted ones included (ADR-0013): IncarnaMind can't tell where an agent sends what it reads, and an agent's report of its own model is a claim we can't check. The line: "Local mode is on, so Codex can't be used: IncarnaMind can't tell where it sends what it reads · Turn off Local mode". This is stricter than #353's design, which blocked only agents with a cloud model.
- **Sync.** Nothing secret syncs: the run grant is never stored, and the agent's keys and sign-in stay in the agent, on that computer. A Conversation's chosen agent is the User's preference and syncs as a model choice does (`providerId` "agent:codex"); whether the agent is set up, its consent and its version belong to the device (portability rules 11 and 12). On a computer without it, the Conversation says so and offers the default model.

**Codex in our sandbox.** macOS won't start Codex's own sandbox inside ours, so Codex runs with its own sandbox off, inside IncarnaMind's. Our sandbox is the wall, and its approvals are the door. That holds only on three conditions:
- **(a)** Codex is offered only after the probe (decision 2) proves the wall: reading a file in the data folder fails inside the sandbox, and a socket other than the shim's is refused.
- **(b)** Its approval policy stays the strictest it has, set at launch and checked as a restrictive mode is, so every file change and every command that writes asks through our approval card, with Allow once and Deny. Under that policy, commands that only read still run without asking, inside our sandbox; the hand test records them and the consent says so. The build checks that codex-acp can set the approval policy apart from the sandbox mode.
- **(c)** Its consent says that Codex's own sandbox is off and IncarnaMind's is in its place (decision 6).

**Codex's ChatGPT sign-in, and its condition.** OpenAI: "If you've built a local or open-source application using Codex app-server authentication, you can continue using it… App-server authentication has never been permitted for commercial or hosted services" ([app-server](https://learn.chatgpt.com/docs/app-server)). The route holds only while IncarnaMind is a local, open-source app with no paid service. A paid tier, or a hosted version, means this is checked again first, and may close the route for Codex's ChatGPT sign-in.

**Gemini CLI, on what it rests.** It stays on the first list on a paid API key, pending the owner's yes. The terms relied on:
- Google, "An important update: transitioning Gemini CLI to Antigravity CLI" (2026-05-19, [blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)): "On June 18, 2026, Gemini CLI and Gemini Code Assist IDE extensions will stop serving requests for Google AI Pro and Ultra, as well as those using it free of charge using Gemini Code Assist for individuals", and "Gemini CLI will remain accessible via paid Gemini and Gemini Enterprise Agent Platform API keys."
- Gemini CLI's own terms page ([`docs/resources/tos-privacy.md`](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/tos-privacy.md)): "Directly accessing the services powering Gemini CLI (for example, the Gemini Code Assist service) using third-party software, tools, or services (for example, using OpenClaw with Gemini CLI OAuth) is a violation of applicable terms and policies." IncarnaMind never touches Gemini CLI's sign-in or the services behind it: it starts the unmodified CLI, which calls the Gemini API with the User's own key.
- The same page: with a Gemini API key, "Your use of Gemini CLI is governed by the [Gemini API Terms of Service](https://ai.google.dev/gemini-api/terms)", whose [paid services](https://ai.google.dev/gemini-api/terms#paid-services) apply to a paid key.

**Later:**
- **Kilo Code** (MIT, an OpenCode fork). Its terms changed hands on 2026-09-30 ([terms](https://kilo.ai/terms)), its npm release lags its source, and after one of its edits is allowed it also asks the client to write the file (`fs/write_text_file`) without checking that the client offered it, so one edit would bring two cards. Listed once a hand test shows how it behaves.
- **Cline** (Apache-2.0). Dropped from #353's list: `cline --acp` stores the `mcpServers` it is given and never connects them (`apps/cli/src/acp/acpAgent.ts`), so it can't reach IncarnaMind's Documents or mint a Citation. Listed if that changes.
- **Claude Code.** Stays on the MCP server (#351), as ADR-0013's addendum decided. Its ACP adapter runs on the Agent SDK, and "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" ([Anthropic](https://code.claude.com/docs/en/agent-sdk/overview)). If it is ever hosted, it is with the adapter's `--hide-claude-auth`, which refuses every turn a claude.ai plan would pay for.
- **Mistral Vibe** (Apache-2.0): Mistral's consumer terms forbid integrating its products with products offered to others without permission ([terms](https://legal.mistral.ai/terms/row-consumer-terms), clause (g)). **Kimi Code**: the registry still points at its archived CLI, and its plan is "for personal interactive use only". **GitHub Copilot CLI** and **Cursor**: proprietary, Copilot's ACP still a public preview.

**Never:** **Antigravity CLI**, whose terms make third-party access a breach ([terms](https://antigravity.google/terms)); **pi** (`pi-acp` stores the client's MCP servers without connecting them) and **OpenClaw** (its bridge rejects them).

**Plans.** IncarnaMind can't tell which key an agent uses, so it can't keep a coding plan out; it only never offers one (decision 7). The plans whose terms forbid this use: Alibaba's Coding Plan ("仅限在编程工具…中使用，禁止以 API 调用的形式用于自动化脚本、自定义应用程序后端…", [Bailian](https://help.aliyun.com/zh/model-studio/coding-plan)), Z.ai's GLM Coding Plan ("may only be used within officially supported tools and products", [Z.ai](https://docs.z.ai/devpack/usage-policy)) and Kimi's.

## Considered options

- **Make the hosted agent a `RunEngine`.** Rejected (ADR-0013's addendum): the model isn't ours, and the engine contract (our Tools, our gate, our window, our temperature) can't be honoured by a loop in another process.
- **Implement `AnswerEngine` for it.** Rejected: most of an `AnswerRequest` (the prompt, the quick model, turn checks that ask again, quote retries, structured output) needs our model. Sharing the Answer's writer keeps what the User sees without pretending to implement the rest.
- **A process per Question.** Rejected: each Question would pay the agent's start (an adapter and its own server), and the agent would forget the Conversation unless every Question carried it all again.
- **One process for the whole app.** Rejected: one crash would end every Conversation, and sessions with different Search scopes would share it.
- **Spawn agents from the core with Node's `child_process`.** Rejected (portability rule 1): the core takes web streams, which a host without Node can give.
- **Run the agent unconfined, and rely on the grant and the consent.** Rejected (decision 2): the agents read files without asking in their most restrictive start, IncarnaMind's data folder holds every Document's text, and what they read goes to their model. The grant bounds only what we hand over.
- **Deny the agent the whole home folder,** as Skill scripts are. Rejected: agents keep their settings, sessions and project tools across the home folder, and denying it would break them in ways each release changes. Denying what is IncarnaMind's and the User's Documents keeps the promise the consent makes.
- **On Linux, allow every Unix socket** so the shim can connect. Not now: it would open the User's other sockets to the agent; Linux waits for a channel that needs none open (decision 2).
- **A localhost HTTP MCP server with a bearer token.** Rejected, as in ADR-0013's addendum: it opens a port a web page can try, and HTTP is optional for agents (`mcpCapabilities.http`).
- **MCP over the ACP connection itself** (`"type": "acp"`, [RFD](https://agentclientprotocol.com/rfds/mcp-over-acp)): no shim, no socket, no grant. Not now: a draft, gated on `mcpCapabilities.acp`, which no agent we list advertises. We move to it when it is stable and they do; it would also end the Linux socket question.
- **Hand the agent a standing pairing (#351).** Rejected: a pairing outlives the Question and has its own Folders, so it would reach more than the Question's Search scope and leave a credential behind.
- **Key tokens to the Conversation,** so that they outlive a Run. Rejected: a token would then pass under a later Question's narrower Search scope. Renewing each prompt's earlier Citations keeps them true without that.
- **Make the hosted assistant's Note edits Proposals** (#352's mechanism), waiting for the User whoever asked. Rejected. The User asked in the assistant, where a change applies at once with one Undo (ADR-0013, 2026-10-21), and the same request would behave differently by which model answered it. The checks that make applying at once safe run in IncarnaMind's write tools, where an edit enters whichever loop called them: the guard on the User's own text, the Citation check, and the card for deletes. What can't run is asking the agent's model again about a claimed change, and the record of what the calls did covers that. Proposals stay for an outside agent acting on its own (decision 4a).
- **Declare no `fs` and no `terminal`,** so that IncarnaMind never writes or runs anything for the agent. Rejected: agents then use their own Tools, whose requests come to the card anyway, and a write IncarnaMind carries out itself keeps ADR-0010's rule for Linked folders, while a command runs through the `Executor`. File reads stay off. v2 removes both capabilities; this is revisited then.
- **For this run, and the agent's `allow_always`.** Not now. For this run would let one click cover a turn whose later calls the User hasn't seen. `allow_always` is kept in the agent's own settings, which IncarnaMind can't show or revoke, and would outlive the turn.
- **Download or bundle an agent's ACP adapter.** Rejected for now: an adapter is code we would vouch for and keep current. Where an agent needs one (Codex), the User installs it with the agent, from its page.
- **Count the agent's reported cost toward the Monthly cap.** Rejected: the cap refuses a request before it is sent, and the agent's requests are its own; a figure it reports after the fact can't stop anything.
- **Let Local mode admit agents that say their model is local.** Not now: the agent's word is all we would have. A later amendment can, given a way to tell.

## Consequences

- `@agentclientprotocol/sdk` 2.0.2 is added, pinned exactly (Apache-2.0, small, maintained by the protocol's own maintainers), the dependency ADR-0013's addendum named. The core imports only its stable v1 entry.
- `src/core/adapters.ts` gains `AgentProcesses`, `AgentProcess` and `AgentProgram`; the desktop app supplies them (`src/main/agentProcesses.ts`), each agent wrapped by `OsSandbox.confineAgent` (`src/main/sandbox.ts`) after `agentSandboxHolds` passes.
- Allowing an agent its vendor's hosts needs sandbox-runtime's network proxy, which the Skill scripts' sandbox doesn't start (it would take the app's SIGINT and SIGTERM). The build starts it in the agents' own helper process (decision 2), with the app's own quit handling kept.
- A hosted session's shim gets a socket of its own outside the data folder; #351's `agents.sock` stays where it is for outside agents.
- `src/core/agents/` gains run grants beside pairings, and the hosted Run. #351's access layer takes either, and looks tokens up by token and caller everywhere.
- **`agent_citations`, a migration** (the next free number at merge, per `AGENTS.md`): the table gains `run_id` (the Run that minted a token; null for a pairing's), and an index on `(pairing_id, token)`. A Run's rows are soft-deleted when it ends, once its Answer holds its Citations. At start, rows whose `pairing_id` is no live pairing (every grant's, after a quit or a crash) are soft-deleted too. Soft deletes and timestamps as ADR-0003 asks.
- The approval requests gain a kind for what an agent would do outside our tools (its own Tool, a file write, a command), with Allow once and Deny and no policy. Deletes use #1274's card as they are.
- A data flow, "hosted-agents", on the Privacy page and in `docs/privacy.md` and `docs/where-your-data-goes.md`.
- The agent list (ADR-0019) gains the hosted fields above. An agent moves on or off the list with a one-line change, when its terms, its ACP support or its hand test change.
- ADR-0013 is amended (2026-11-01): the addendum's rejected option "Let agents write to Minds directly" now holds only for an outside agent on its own; the hosted assistant edits in place with Undo. Its line that outside agents aren't offered the commands no longer holds for a hosted Run.
- #353's design shows the agent's name and version, not its sign-in, and its acceptance criteria follow this record once it is accepted (no Proposals, no "For this run").
- CONTEXT.md gains a term for the User's agent running the assistant when this is built.
- Before release, each listed agent is tried by hand with the cheapest model that answers (`AGENTS.md`), its "runs without asking" filled in from that, and its terms read again.
- #352 keeps Proposals for outside agents acting on their own over MCP, and exposes decision 4a's interface; #353 doesn't wait on it, since a hosted Run uses the write tools.
