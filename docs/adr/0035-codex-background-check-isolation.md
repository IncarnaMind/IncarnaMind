# A Note Check runs on Codex in the background, held by a model catalog, a preflight and a watch

When the User presses Check with Codex connected, its command line on this computer and no model set up in IncarnaMind, IncarnaMind runs the check on the User's own Codex in the background, as it does on Claude Code ([ADR-0032](0032-a-check-runs-on-the-users-own-command-line-ai.md)): nothing opens, no chat is added, the Note says it is being checked with Stop beside it, and the marks land. Where any of what follows doesn't hold, the check goes by the link, as before. [Issue and acceptance criteria](https://github.com/IncarnaMind/IncarnaMind/issues/3639)

The proposal of 2026-11-22 kept the link because two prerequisites were outstanding on Codex 0.170.0: a sign-in usable from an isolated run, and a complete policy that refuses Codex's own tools before they run. Further runs on 0.170.0 met the second and all of the first but one input: the User's global `AGENTS.md`, which the User is told of where they consent. The owner decided on 2026-11-23 to build it on that basis.

This corrects ADR-0032 decision 3, which found that Codex reaches IncarnaMind's Tools only through code mode. With the model catalog below, code mode is off and Codex calls the server's Tools directly.

## The run

`codex exec --json --ephemeral --ignore-user-config --ignore-rules --strict-config --skip-git-repo-check --sandbox read-only`, the prompt on stdin, in the User's own Codex folder, so Codex reads its own sign-in and IncarnaMind touches none. With it:

- **A model catalog** (`model_catalog_json`), built at each run from the installed binary's own (`codex debug models --bundled`) with five fields of every model changed: `tool_mode = "direct"`, `apply_patch_tool_type = null`, `multi_agent_version = null`, `experimental_supported_tools = []`, `supports_search_tool = false`. The request then lists only IncarnaMind's Tools and Codex's three MCP resource operations; of those, the watch lets only one that names IncarnaMind's server go on. Without the catalog it lists code mode's `exec` and `wait`, with `apply_patch`, a clock and sub-agents inside.
- **Approvals `never`,** IncarnaMind's server with `enabled_tools` set to the check's six Tools and `default_tools_approval_mode = "approve"`, and the features that give the model a tool, an app or a hook turned off, among them the shell, unified exec, apps, plugins, hooks, memories, goals, sub-agents, image tools and the browsers; `features.multi_agent_v2.disable_native_tools`, `tools.experimental_request_user_input.enabled = false`, `web_search = "disabled"` and `project_doc_max_bytes = 0`.
- **Nothing of the run in the User's Codex folder,** each held off by what Codex 0.170.0's source and runs show: no session, thread lock or index (`--ephemeral`); its state and log databases, which hold the Note's text, in the run's own folder (`sqlite_home`, `log_dir`); no shell snapshot (`shell_snapshot` off: a snapshot exports Codex's environment, and so the grant, into the User's Codex folder); no refresh of the models cache (the catalog makes Codex's list static); no bundled skills installed (`skills.bundled.enabled = false`); no plugin or app caches (`plugins`, `apps` off); no rules migration (`--ignore-rules`); no trusted-folder entry in the User's config (a read-only sandbox, and never `--trust`); no memories, no rollout maintenance and no agent identity (`memories`, `local_thread_store_compression`, `background_paginated_rollout_migration`, `use_agent_identity` off); no daemon (`daemon_auto_start` off); no history (`history.persistence = "none"`; exec writes none anyway); analytics and OpenTelemetry export off.
- **The grant** reaches IncarnaMind's server from Codex's environment, named in `env_vars`, never on the command line. IncarnaMind's instructions go in `developer_instructions`, written as TOML so no line break reaches the command line.
- **The model** is Codex's own default with nothing set: by priority, the first model its picker lists among those the sign-in may use. The User's own choice in their config is dropped with the rest of it, as Claude Code's is (ADR-0032 decision 3).

What runs on 0.170.0 showed: every call to a tool the request doesn't list (`apply_patch` in both forms, `exec_command`, `shell`, `spawn_agent`, code mode's `exec`, `view_image`, `request_user_input`, a server Tool left out of `enabled_tools`) gets "unsupported call" back from Codex before it runs, and leaves no event, no server call and no file.

## Before every run

Each of these, or the check goes by the link, with nothing said about the fallback itself:

- `codex` on the login shell's PATH, as a terminal finds it, whose real path is not inside an app (`*.app`, or a Windows app's `WindowsApps` folder): never the copy the ChatGPT app ships for itself. The documented installs (the standalone installer, npm, Homebrew) all resolve outside one.
- `codex --version` at least 0.170.0, the only version this was measured on. A later one runs only through the preflight.
- `codex login status` exiting 0. Nothing else it prints is read; a definite sign-out, a sign-in it can't read and no answer all go by the link.
- **A free preflight:** `codex debug prompt-input`, given the run's own settings in a Codex folder of the run's own, must print exactly the six Tools and the three resource operations, for each model Codex could use with none set (without a model, and pinned to a sign-in to ChatGPT's default where that is another model). It makes no model request. A feature switch this Codex doesn't know makes it fail, and so does a server that doesn't start.
- **What the preflight can't see.** It runs in a Codex folder of the run's own, because `codex debug prompt-input` takes no `--ignore-user-config`: run in the User's own folder it starts their MCP servers and lists their tools (a run with a synthetic used profile listed its server's tool and `request_permissions`). So it can't see what reaches the run only from the User's folder or sign-in: an organisation's settings fetched for a business, education or enterprise plan, and anything a managed configuration adds there. Their skills it does see, from their home folder. Against those layers less holds than against the User's own settings. The read-only sandbox holds Codex's own shell and patch tools, not a tool on an MCP server a managed configuration adds, which runs as the User. Approvals `never` stops such a call only where that configuration hasn't set the server's tools to be approved. The grant covers IncarnaMind's server only. The watch stops the run at the first item it doesn't allow, which it sees only once the call has started, so at most one such call can start. What an organisation's cloud settings can add was not measured.
- `codex exec` must start its turn. One that ends first sent nothing to a model: a setting it doesn't know (`--strict-config` refuses one before anything else), or a flag it doesn't take. So a switch renamed in a later Codex, a feature in the preflight or a setting in the run, leaves the check to the link. A setting Codex goes on accepting but no longer honours can't be caught this way.

## While it runs

The flags are the wall; IncarnaMind watches the event stream for a sign that one didn't hold. Thread and turn starts and ends, and the service's own error notices, pass. Of the items, only the agent's messages, its reasoning, calls to the six Tools on IncarnaMind's server and Codex's three resource operations naming IncarnaMind's server (which serves no resources), under its name, pass. On Codex 0.170.0 (a loopback run with a second server configured) a read or list naming another configured server comes as an item under that server's name, and a list naming no server as one under Codex's own name, which asks every configured server: each stops the run, after that one call. A call naming a server Codex doesn't have comes as no item, and Codex asks no server for it. Before the turn starts, anything else means nothing reached a model, and the check goes by the link. Anything else ends the run, the grant is revoked and the line says "Codex stopped because it requested an action outside this check. Open the check in Codex.", with Ask by its link as the one action. A line that can't be read, or an event Codex didn't have, ends it with "Codex stopped before finishing. Open the check in Codex." A turn that fails says "Codex stopped before finishing. Check your sign-in and usage in Codex.": Codex gives its errors no category (a plan's limit and a model the plan doesn't include both come as a message), so IncarnaMind doesn't guess which. The rest of ADR-0032's limits apply: 15 minutes, six minutes of silence while no Tool of IncarnaMind's runs, a bounded output.

## Stop and what is left

Stop, quitting, disconnecting, Local mode, a take-back and the Note leaving the agent's reach end Codex's process group (its process tree on Windows), drain its output and revoke the grant, which closes the server's connection: the server Codex started, in a process group of its own, exits with it. The run's folder (mode 0700: the working folder, the catalog, the preflight's Codex folder and the redirected databases, whose log holds Note text) is removed when the run ends, and a folder whose app is gone is removed at the next start. A report that landed before Stop stays, as on Claude Code.

On Codex 0.170.0, nothing of the run is kept in the User's Codex folder; before each release the measurement is taken again on the Codex then current (`docs/agents/checks.md`), because a later Codex could keep accepting a setting and stop honouring it. What Codex itself still writes there, holding nothing of the run, and nothing can turn off:

- its launcher folder (`tmp/arg0-<platform>/codex-arg0…`: a lock and two links to its own binary), which every start replaces, the User's own included;
- its sign-in (`auth.json`), when the token is due for renewal or the service refuses it, as on any use;
- `installation_id`, only if it is missing, as at a first start;
- on a business, education or enterprise plan, its cache of the organisation's settings (`cloud-config-bundle-cache.json`), as at any start.

A managed configuration file an administrator installs (`/etc/codex/managed_config.toml`, or its macOS profile) comes before the run's own settings in Codex 0.170.0's order (`config/src/loader/README.md`). So it can put the databases and logs, the Note's text among them, where it says, kept after the run, and change any other setting above; the preflight reads it, but checks only the Tools it offers. Organisation cloud settings and the system's `config.toml` come after the run's settings, so they can only add what the run doesn't set, such as a server. Not run: no such file was installed.

## What the User is told

Where they connect Codex: "With no AI model set up here, Check runs your Codex command line in the background, if it is installed. Nothing opens and no chat is added. It may use only IncarnaMind, which stops it at anything else. It uses your own ChatGPT plan or API key. In these runs Codex also reads your own instructions file, AGENTS.md in your Codex folder (or AGENTS.override.md, if you have one)." A connection made before asks once, in the consent dialog, with the last sentence. Connecting Codex agrees to the check only: a request typed at a Note's foot stays on the link (ADR-0034) and would ask again.

The one input that can't be held off: Codex 0.170.0 always loads `$CODEX_HOME/AGENTS.md`, or `AGENTS.override.md` instead where that file is (a loopback run with each and both), into the request, whatever the flags (`codex-home/src/instructions/mod.rs`). It adds no tool; it can only steer how the model checks.

## Measured, and not

On macOS, Codex 0.170.0 (the standalone install), a signed-in throwaway profile, the test build and the real shim: an English, a Chinese and a planted Note each landed both marks right (07:30 supported, 40 bicycles contradicted by 24), with only the six Tools called and nothing outside them asked for; Notes of eight and twenty sentences landed their marks; Stop after the first Tool call cleared the line in 140 ms, and Codex and the server were gone within 2.5 s. The profile's file listing (names, sizes, times) changed only in Codex's launcher folder: after those runs together, and after each long one alone; on loopback, with a copy of a used profile, after a run of 77 seconds, one stopped at 30 seconds and one that failed with a 400, the same. One run before `shell_snapshot` was off left a snapshot in the profile. Checking with the catalog and the preflight took 269 ms (median of 10, worst 325), and a press reached its start in 460 ms. The Windows and Linux process trees are proven with a stand-in for Codex in the packaged app's checks, not with Codex itself. Not verified: Windows and Linux with the real Codex, a managed (organisation) configuration, the operating system's credential store, a token refresh during a run, plans without the default model, and the ChatGPT desktop app running beside a run.
